# Repo Lore

> Repo Lore builds a living, evidence-backed mental model of a software repository so an unfamiliar engineer can understand it with justified confidence — without relying on tribal knowledge.

Paste a public GitHub repository URL — or just type its `owner/repo` (e.g. `nielse63/RepoLore`) — and Repo Lore produces a stable, readable "lore" page for it at `/lore/{owner}/{repo}`: what the repository contains, where to start reading and why, its major structural areas, probable entry points, and how those areas directly relate. Every important conclusion links back to the source evidence it came from and is labeled **Detected**, **Inferred**, **Unknown**, or **Unsupported**. Repo Lore does not refresh automatically — you can manually request a fresh analysis after the repository changes.

Repo Lore earns confidence through evidence, not AI narration. Analysis starts with deterministic source and dependency analysis, repository configuration and metadata, and explicit heuristics. AI is not required; when introduced, it only explains and organizes findings that have already been established as fact — it never replaces the analysis itself.

## Status

Phase 2 (scaffolding) is underway, and the first end-to-end slice works for JavaScript/TypeScript: paste a public GitHub repository URL on the home page (`/`) and Repo Lore validates it, resolves its default branch and HEAD commit via the GitHub API (`src/github/`), fetches and safely extracts its tarball (`src/acquisition/` — non-regular entries like symlinks are skipped, not fatal, and disclosed as a gap rather than failing the whole run), runs the JS/TS analyzer (`src/analysis/js-ts/`) — imports/exports, internal dependency edges (including path-aliased imports, resolved against `tsconfig.json`/`jsconfig.json`, `package.json`'s `imports` field, and common bundler/framework configs like `vite.config.*`/`webpack.config.*` — ADR-0015), entry points, public surface, test relationships, React components, an application-vs-library `project.kind` inference (manifest `main`/`exports` shape, overridden by a detected UI framework dependency or UI components in source), Start Here and major-area derived views — persists the result to Postgres (`src/db/`, idempotent per ADR-0005), and redirects to a stable `/lore/{owner}/{repo}` page rendering it with a Detected/Inferred/Unknown/Unsupported certainty label on every claim and a GitHub link back to its source. A failed or partially-supported analysis still renders honestly there rather than silently disappearing, and a rate-limited "Re-analyze" button on that page (`src/analysis/reanalysis-rate-limit.ts`, its icon spinning while the request is in flight) re-checks the repository's HEAD and re-runs analysis if it's moved, reporting honestly when there's nothing new to analyze. Since analysis runs synchronously inside the home page's submit Server Action, the form is replaced in place by a staged loading view (a spinning icon plus a label cycling through "Fetching repository source…", "Analyzing code…", "Building your Lore…" — narration of the real pipeline's phases, not measured progress) until it redirects to the finished page. Requires `GITHUB_TOKEN` and `DATABASE_URL`. A Python analyzer (`src/analysis/python/`, ADR-0006: tree-sitter-python via `web-tree-sitter`, syntactic-only) now exists and produces the same project/relationships/entry-points/public-contracts/test-relationships shape as the JS/TS analyzer, plus its own Start Here/major-area derived views (`src/analysis/python/derive-views.ts`, sharing a language-neutral core with JS/TS at `src/analysis/shared/derive-views.ts`) — validated against `fixtures/python-app`, `fixtures/python-library`, and three real public Python repositories. Every real `/lore/{owner}/{repo}` submission now runs a real language-detection dispatch step (ADR-0007, `src/analysis/dispatch/`): GitHub's byte-weighted `languages` API decides which analyzer(s) actually run, every supported language (JavaScript/TypeScript together, or Python) at or above a 10% byte share gets its own analyzer run and its own project in the result, and a repository whose language isn't supported at all is honestly persisted as a failed run naming what GitHub actually detected, rather than silently analyzed as the wrong language.

The UI now has a full design system (see "Design system and UI routes" below) applied to the home page, the real `/lore/{owner}/{repo}` overview, the real `/lore/{owner}/{repo}/architecture` page (ADR-0008), the real `/lore/{owner}/{repo}/history` page (ADR-0010, a deliberate, scoped override of the commit-history-analysis exclusion — see below), and the real `/lore/{owner}/{repo}/dependencies` page (ADR-0011: external dependency extraction from `package.json`/`pyproject.toml`, matched against import usage, plus a live npm/PyPI registry description lookup and an Internal tab reusing Architecture's area-relationship data), the real `/lore/{owner}/{repo}/data-flow` page (ADR-0012: a function-level call tree, JS/TS only), and the real `/lore/{owner}/{repo}/systems` page (ADR-0014: a renamed, re-presented view of the existing Major Area model — list and per-area subview, no new analyzer capability), plus the remaining view scaffolded under `/lore/{owner}/{repo}/*` with static example content, since the analysis behind it doesn't exist yet — see "Design system and UI routes" below.

## Initial scope

- Public GitHub repositories only (no auth, no private repos, no payments yet).
- TypeScript, JavaScript, and Python applications and libraries, sharing one language-neutral Lore model. React is framework-aware enrichment within the JavaScript/TypeScript analyzer, not a separate product.
- One deterministic vertical slice: submit a URL, get a Lore page with repository orientation, a "Start Here" reading path, a major-area model, probable entry points and direct relationships, and evidence with explicit gaps — all traceable to source.

See `docs/product/mission.md` and `docs/product/non-goals.md` for the product foundation.

## Design system and UI routes

The UI is built with Tailwind CSS v4 (`src/app/globals.css` defines the color/font tokens as CSS custom properties, themed for light and dark via `prefers-color-scheme`) plus a handful of Radix UI primitives (`@radix-ui/react-tabs`, `-switch`, `-dialog`) for accessible tab, toggle, and drawer/sheet behavior, and `lucide-react` for icons. Reusable design-system components live in `src/components/ui/` (Card, Badge, IconTile, Button, Tabs, Table, SearchInput, FilterPills, StepList, Pagination, Drawer, …) and the shared `/lore/{owner}/{repo}` page shell (Sidebar, TopBar, RepoIdentity, RightRailShell, LorePageFrame) lives in `src/components/lore-shell/`. Headings use a serif display font (Source Serif 4) paired with Geist Sans for UI text.

The shell is responsive down to phone width behind a single `lg` (1024px) breakpoint — above it, the Sidebar and right-analysis-rail render at full width; below it, the Sidebar becomes a hamburger-triggered off-canvas drawer (`MobileNavContext`/`MobileNavTrigger`) and `RightRailShell` additionally renders a floating "Details" trigger opening the same content as a bottom sheet, so no desktop-only feature (including the Systems page's dependency diagram, which only ever lived in the rail) is unreachable on mobile. Both use the shared `src/components/ui/Drawer.tsx` primitive.

Every view has a route under `/lore/{owner}/{repo}/`:

- **Real, backed by actual analysis:** the overview page (`/lore/{owner}/{repo}`), the home page (`/`), the architecture page (`/lore/{owner}/{repo}/architecture`), the history page (`/lore/{owner}/{repo}/history`), the dependencies page (`/lore/{owner}/{repo}/dependencies`), the data flow page (`/lore/{owner}/{repo}/data-flow`), and the systems page (`/lore/{owner}/{repo}/systems`). Overview and Architecture render only what the `Lore` model already produces — Major Areas, the direct relationships between them, Entry Points, and each project's `frameworks` — as evidence-backed lists/tables, per **ADR-0008**: no infrastructure/data-store detection, no framework detection beyond what the analyzers already support, and no "architectural boundaries" narrative claims, since none of those are backed by real evidence today. As a narrow, deliberate exception recorded in **ADR-0009** and amended by **ADR-0016**, the Major-Area relationships are additionally shown as a dependency diagram (`@dagrejs/dagre` for layout, rendered client-side with `@xyflow/react` for pan/zoom/`fitView` navigation only — dragging, connecting, and selection are explicitly disabled; still no file-level graph) on both pages. The diagram only lays out areas with at least one production relationship. Areas with none are listed under it as "Not connected to other areas" instead of being placed in the top rank, where they used to widen the graph. `fitView` can zoom out to 0.05 (react-flow's default `minZoom` of 0.5 clamped it and clipped wide graphs), and edges use the `--muted` token rather than `--border` so they stay visible. The Systems rail's copy links to the Architecture diagram with "View full diagram" (GitHub issue #51). Above `MAX_DIAGRAM_AREAS` (30) connected areas, the diagram used to disappear (Architecture, Overview) or claim there weren't enough systems (Systems rail), so large repositories like react/react and sveltejs/svelte had none. It now draws the 30 areas with the most detected production relationships (distinct neighbor areas, in or out, ties by name) and only the edges among them. A caption gives the shown and connected counts, notes that unresolved imports are Unknown, and links to Component Connections for the full list. Unconnected areas are then counted rather than listed. A System subview always keeps its own area and counts neighbors instead. The wording sticks to "detected relationships", never importance (ADR-0014). History is itself a deliberate, scoped override of the commit-and-pull-request-history-analysis exclusion (product owner's explicit decision, against a `product-scope-guardian` recommendation not to build it yet): it lists commits from the GitHub API (`src/github/commits.ts`), classifies each commit's diff via deterministic regex/path-convention heuristics against the last persisted `Lore` (`src/history/classify.ts` — dependency-manifest, cross-area relative-import, and data-layer-path changes, every fact `inferred`/`unknown` certainty, never `detected`; `package.json` lines count only inside a dependency section when the hunk shows the enclosing object (otherwise only with a version-spec-shaped value), a `package-lock.json` diff becomes one "N packages changed" fact ("at least N" when some changed lines fall outside any visible package entry) counting its changed `node_modules/…` entries, and `yarn.lock`/`pnpm-lock.yaml` diffs one `unknown` fact rather than per-line guesses — GitHub issue #41; History rows cached before that fix keep their old text until "Refresh history"), and describes entries with fixed templates rather than an LLM call. It deliberately omits the mockup's before/after diagram, Evidence Library link, and interactive date-range picker. Dependencies (**ADR-0011**) extracts real external (`package.json`/`pyproject.toml`) dependencies and matches them to importing files — `detected` for JS/TS's exact bare-specifier match, `inferred` for Python's name-normalization match, since Python import names often differ from their PyPI distribution name — with two deliberate overrides of that ADR's own scope-guardian review: a live npm/PyPI registry description lookup (bounded, non-fatal, no cross-repo cache in v1) and a small, closed, purely cosmetic package-name-to-icon category map. Its Internal tab reuses Architecture's area-relationship data rather than computing anything new. That Area → "Depends on" table (`AreaRelationshipsTable`, also Architecture's Component Connections) is paginated by `PaginatedTable`, `PaginatedList`'s table counterpart: the same fit-to-screen page size (up to 15 rows) and a page remembered per repository and page for the tab session. Data Flow (**ADR-0012**) renders a function-level call tree — named functions/methods/arrow-function-expressions and the statically-resolved direct calls between them (JS/TS only; syntactic, never type-checked) — rooted at the repo's exported and framework-entry-point functions (`src/lore/call-tree.ts`), each row expandable in place to reveal its callees, arbitrarily nested, with a right-rail detail panel (parameters, return type, callers/callees, evidence) that updates as you drill down. The page opens in its List view sorted by importance (highest `FunctionImportance` score first, ties by name — `src/lore/function-ranking.ts`), with the detail panel focused on that top-ranked function; the call tree (Chain) and the alphabetical Name sort are one click away (GitHub issue #7). The List view is paginated like the Dependencies table (a page size that fits the screen at load, up to 15 rows — rows put the name and path on one line when the list is at least 42rem wide, so about 7 fit below the header at an 800px-tall viewport; the page is remembered per repository for the tab session and resets to 1 when the search or sort changes) instead of being capped at 200 rows. A prior interactive diagram view has been removed pending a revisit once the tree view has seen more real repos. Systems (**ADR-0014**) is a renamed, re-presented view of the existing Major Area model — no new analyzer capability, no infrastructure/data-store nodes (an explicit rejection of the mockup’s invented Core/Supporting/Data typing and Postgres/Redis nodes, per ADR-0008’s existing boundary). Each Major Area is classified `"Implementation area"`, `"Tests / test support"`, or `"Build/tooling configuration"` (`src/lore/system-classification.ts`, wording reused verbatim from `AreaDependencyDiagram.tsx`, deliberately not a criticality/importance judgment), searchable/filterable client-side; each area also gets a stable-within-a-run kebab-case slug (`src/lore/system-slug.ts`) for its `/systems/{slug}` subview, which shows responsibilities, owned locations, a relationship diagram scoped to its immediate neighborhood, key entry points, and evidence. The Sidebar link, previously commented out, is restored. Overview's Major Areas grid is paginated through the URL (`?page=N`, 6 cards per page, out-of-range values clamped by `src/lib/page-param.ts`) so the server renders only the current page's cards — serializing every card for client-side pagination made a repository with thousands of Major Areas take tens of seconds to render. See ADR-0008, ADR-0009, ADR-0010, ADR-0011, ADR-0012, ADR-0014, and ADR-0016 for the full reasoning.
- **How Major Areas are grouped:** files are grouped by directory (two levels deep), and any group over 10 files is split one directory level deeper (`src/analysis/shared/derive-views.ts`). A conventional test directory (`test`, `tests`, `__tests__`, `e2e`) at any depth is never split: it stays one area labeled Tests, and its files are left out of `productionFilePaths`. When a file there doesn't match the language's own test-file convention, the evidence says it's grouped as a test by directory name only. The directory name is overruled when detected structure contradicts it: a non-test entry point inside it (e.g. a Next.js `app/test/page.tsx` route), or production code outside any test directory importing from it (e.g. Django's shipped `django/test/` package). The area is then left unlabeled, its files count as production, and its evidence cites the contradiction. Without that rule, a suite like Svelte's `packages/svelte/tests/<suite>/samples/<case>/` turned into one area per sample case, 2,994 in all (GitHub issue #50). Analyzer versions `js-ts-v15`/`python-v8` carry this change. File-level analysis applies the same rule, but only to remove candidates. A file under an uncontradicted nested test directory is never detected as a bootstrap entry point (a `ReactDOM` render/`createRoot` call, or an `if __name__ == "__main__":` guard) or, for Python, as a `__main__.py` cli entry point, and never reported as the implementation a test covers. It isn't counted as a test file either, so a harness like `pkg/tests/run_all.py` can't become Start Here's first step, and a test's helper import can't become its subject (GitHub issue #65). When a test's local imports resolve only to such files and no naming convention matches, its Unknown gap says so rather than implying nothing resolved. For this check, the contradiction is judged from import relationships and declared entry points (package.json fields, console scripts), never from these heuristics' own results. Analyzer versions `js-ts-v17`/`python-v10` carry this change.
- **At a glance:** the Overview opens with a short "At a glance" card above Start Here (GitHub issue #59), built by `buildAtAGlance` (`src/lore/at-a-glance.ts`) from facts already in the stored `Lore`. There is no AI and no new analysis, so no analyzer version bump. It has at most four lines. The first gives the kind and languages. A single project is named after the repository, because a project with no manifest name is stored as the placeholder `source`. A mixed-language repository (ADR-0007) gives each language project its own row in the kind and entry-point lines. Kind is always labeled Inferred, because both extractors classify it heuristically. It is followed by the reason from the kind evidence, such as "because a bootstrap or command-line entry point was found at `src/index.tsx`". The no-`"main"`/`"exports"` fallback reads "assumed because `package.json` declares neither…". An unrecognized evidence kind falls back to the evidence's stored description. The second names the starting entry point, chosen per project the way Start Here's first step chooses it: a bootstrap or CLI entry point, otherwise a declared library or runtime entry point. Any further entry points are counted and linked to the Entry Points list. The third names up to three implementation areas with the most detected direct relationships, using the Major Areas ranking and showing each count. The fourth gives counts of Major Areas, external dependencies (with the production count) and recorded gaps. A missing fact, such as an unknown kind, no starting entry point, or no detected area relationships, is stated as Unknown instead of the line being dropped. On a partial run, the partial-analysis warning appears above the card. The card's claims were checked with the `analysis-integrity-reviewer` subagent. `e2e/at-a-glance.spec.ts` checks it against the seeded application, library, mixed-language, partial, and `nielse63/RepoLore` Lores.
- **How Major Areas are ordered:** areas are persisted alphabetically, but every Major Area list (Overview, Architecture, Systems) shows them ranked by `rankMajorAreas` (`src/lore/major-areas.ts`), so the first page isn't a run of unrelated `docs/` or `examples/` directories (GitHub issue #48). The ranking puts implementation areas before tests, test-support and tooling areas, then sorts by direct relationship count (depends on + imported by), then entry-point count, then name. A note above each list says so. Relationship counts only include imports the analysis resolved, so a 0 can mean the relationships are unknown. When no area in a list has a detected relationship, the note says the order comes from entry points and name instead. Ranking happens at presentation time, so there's no analyzer version bump. Systems slugs and the dependency diagrams still use the persisted order, so existing `/systems/{slug}` URLs keep resolving to the same areas.
- **Deliberately not built:** an Evidence Library view (deferred for later reconciliation, per product direction).

Every repository route now has its own `generateMetadata` (unique `<title>`, description, self-referencing canonical, Open Graph/Twitter cards), a skip-to-content link, named landmark regions, and a corrected heading hierarchy, following an external UX/SEO/accessibility audit.

### Search, sharing, and README badges

Per **ADR-0017** (approved after a `product-scope-guardian` review), a repository's Overview (`/lore/{owner}/{repo}`) is `index, follow` only when `isIndexableLore` (`src/lib/lore-indexability.ts`) holds for its latest run: `completed` (not `partial` or `failed`), public, with at least one entry point and one Major Area. Every other Overview, and every subview, stays `noindex, follow`. Once it has an analysis, the Overview's `<title>` and meta description are worded for how people search for a codebase (`loreOverviewTitle`/`loreOverviewDescription` in `src/lib/route-metadata.ts`): `{owner}/{repo}: codebase architecture & entry points — Repo Lore`, and a description leading with the repository's own GitHub description (truncated) followed by the same entry point, Major Area, and Start Here counts the page renders — entry points as "probable" (each carries its own certainty label), and a partial run labeled as partial, per an `analysis-integrity-reviewer` pass. The title falls back to the plain `{owner}/{repo} — Repo Lore` when there are no entry points or Major Areas to show, and both stay generic for an unanalyzed or failed run (even one that persisted a result). The same rule drives `src/app/sitemap.ts` (home, `/explore`, `/manifesto`, and every indexable Overview, read from Postgres per request, degrading to just those static pages if the database is unreachable) and the per-repository Open Graph card (`src/app/lore/[owner]/[repo]/opengraph-image.tsx` — repository name plus entry point/Major Area counts, or a generic tagline when the run doesn't qualify). `src/app/robots.ts` allows everything except `/api/` and points at the sitemap. Since indexed pages invite crawler traffic, the layout skips the ADR-0013 pull-triggered background re-analysis for crawler user agents (`src/lib/is-crawler-user-agent.ts`), so a crawl never becomes a visitor-less refresh. Every Major Area count — the Overview and other pages, `isIndexableLore`, the Open Graph card, `/explore` and home cards (via SQL in `listLatestRunIndexabilityFacts`), and the meta description — goes through `majorAreasOf` (`src/lore/major-areas.ts`), which excludes the root `"."` area, so none can disagree with what the Overview lists. The same rule also feeds internal links, so crawlers and visitors reach indexable Lores without the sitemap: `/explore` (`src/app/explore/page.tsx`) lists every indexable Lore as a card (description plus entry point/Major Area counts, `src/components/LoreCard.tsx`), and the home page shows up to six example Lores below the form — `FEATURED_REPOS` (`src/lib/featured-lores.ts`, the six seeded repositories) first, then the most recently analyzed others — with a "Browse all Lores" link. Both read Postgres per request (`force-dynamic`, so `npm run build` still needs no `DATABASE_URL`) and hide the list rather than erroring if the database is unreachable. Pages outside a Lore (home, `/explore`, `/manifesto`, not-found, an unanalyzed repository) share `SiteShell` (`src/components/SiteShell.tsx`): `SiteHeader` (wordmark home link plus `/explore`) and `SiteFooter` (Manifesto, Explore Lores, the GitHub repository, and a copyright line ending with the app version — the latest git tag reachable from the built commit, read by `git describe --tags --abbrev=0` in `next.config.ts` via `src/lib/app-version.ts` and inlined as `APP_VERSION`, omitted when the build's clone has no tags). On Lore pages the same footer sits at the end of `LorePageFrame`'s scrolling column, beside `<main>` rather than inside it so it keeps its `contentinfo` landmark. `/manifesto` (`src/app/manifesto/page.tsx`) is a static, indexable page with the text of the "The Repo Lore Manifesto" Notion doc, and is listed in the sitemap. Like DeepWiki, swapping `github.com` for `repolore.app` in any GitHub URL works: a root catch-all route (`src/app/[...path]/page.tsx`, parsing via `src/lib/repo-from-swapped-path.ts`) turns `/{owner}/{repo}/…` or `/github.com/{owner}/{repo}/…` into a temporary (307) redirect to `/lore/{owner}/{repo}`, ignoring ref/path segments; the app's own top-level routes (`lore`, `explore`, `api`, `_next`) are never read as owners, and anything else 404s as before. It does no database read or GitHub call. A `/lore/{owner}/{repo}` with no persisted run now renders `NotAnalyzedPanel` (`noindex`, no sidebar) instead of a 404: an explicit "Analyze {owner}/{repo}" button that submits the home page's own `resolveRepository` Server Action (same validation and rate limits), so a page view — including a crawler's — never starts analysis. Its subviews still 404. The Overview's Analysis rail has an "Add a README badge" card (`ReadmeBadgeCard`) with copyable Markdown linking the static `public/badge.svg` to the repository's Lore URL (`src/lib/readme-badge.ts`).

## Analytics

Google Analytics (`gtag.js`, measurement ID `G-66W4D723ZX`) is loaded on every route via `next/script` in the root layout (`src/app/layout.tsx`), `strategy="afterInteractive"` so it never blocks the initial render. `next.config.ts`'s CSP explicitly allowlists `googletagmanager.com`/`google-analytics.com` for `script-src`/`connect-src` — anything not on that list stays blocked. Custom events go through `trackEvent` (`src/lib/analytics.ts`, a no-op wherever `gtag` isn't loaded): `submit_repo` when the home form is submitted and `submit_repo_error` when it's rejected with an inline error before any run exists, and — once a submission's analysis finishes — `analysis_completed`, `analysis_partial`, or `analysis_failed`. The Server Action redirects before the client sees the result, so it redirects to `/lore/{owner}/{repo}?submitted=1`; the Overview then renders `SubmissionOutcomeEvent` (`src/components/SubmissionOutcomeEvent.tsx`) with the latest run's status, which fires the event and strips the marker from the address bar so refreshes and copied links don't re-report it (the canonical URL never includes it). Per-Lore page views and outbound GitHub link clicks rely on GA4's enhanced measurement (page views including history changes, outbound clicks), so they need no custom code — keep it enabled on the web stream.

## Fixtures

`fixtures/` holds small, hand-built local repos used to develop and sanity-check each language analyzer before it's run against real repositories. Two scripts also give manual, human-readable sanity checks against a fixture (in addition to the automated unit test suite — see "Testing" below):

```
npm run discover -- fixtures/ts-react-app   # source file discovery + exclusion rules
npm run extract -- fixtures/ts-react-app    # full JS/TS project extraction
npm run derive -- fixtures/ts-react-app     # Start Here + major-area derived views
npm run discover -- fixtures/ts-library
npm run extract -- fixtures/ts-library
npm run derive -- fixtures/ts-library
```

The Python analyzer (`src/analysis/python/`) has its own equivalent scripts (source discovery is folded into extraction, so there's no separate `discover-python`):

```
npm run extract-python -- fixtures/python-app
npm run derive-python -- fixtures/python-app
npm run extract-python -- fixtures/python-library
npm run derive-python -- fixtures/python-library
```

Each local fixture also has a matching private GitHub repository (`nielse63/repo-lore-{ts-react-app,ts-library,python-app,python-library}-fixture`) with the same source, used to exercise the real submit → analyze → `/lore/{owner}/{repo}` flow end-to-end. The exceptions are `fixtures/mixed-ts-python` (a TypeScript library and a Python CLI sharing one root, analyzed by both analyzers), `fixtures/js-partial` (a single-file project that falls short of the minimum value contract, so it persists as `partial`), both seeded for `e2e/at-a-glance.spec.ts`, `fixtures/python-only` (a Python-only package, seeded for `e2e/data-flow-default.spec.ts`'s no-functions empty state), `fixtures/ts-many-areas` (a hub area importing 33 one-file module areas, seeded for `e2e/area-dependency-diagram.spec.ts`'s above-the-ceiling diagram), and `fixtures/ts-nested-test-samples`, a local-only fixture that reproduces GitHub issue #50's Svelte-shaped layout (many one-file sample-case directories nested under `packages/core/tests`). `npm run seed:e2e` persists it for `e2e/nested-test-samples.spec.ts`, along with a History cache built by the real classifier from recorded GitHub commit payloads in `fixtures/history-commits` (a lockfile-only bump and a `package.json` edit, GitHub issue #41) for `e2e/history-dependencies.spec.ts`.

## Testing

Automated tests are both unit (Jest) and functional (Playwright).

### Unit tests (Jest)

Every source file under `src/` has a matching Jest unit test at `<same-directory>/__tests__/<file>.spec.ts`. Run the full suite with `npm run test:unit` (`npm run test:unit:watch` for watch mode, `npm run test:unit:coverage` for a coverage report).

- Jest is configured via `next/jest` (`jest.config.ts`), which handles the Next.js/SWC transform; tests run in the `node` environment (no jsdom/UI component tests — that's what the Playwright suite below covers).
- The JS/TS analyzer tests (`src/analysis/js-ts/`) exercise a real in-memory `ts-morph` `Project` rather than mocking its AST — ts-morph is a pure, in-process parser with no network or native-binding dependency, so this is both more realistic and simpler than hand-mocking `SourceFile` objects.
- The Python analyzer tests (`src/analysis/python/`) similarly parse small real Python source snippets with the real `tree-sitter-python` grammar (`createPythonParser`/`parsePythonSource`) rather than mocking tree-sitter's `Node` interface — it's a bundled, offline WASM grammar with no network dependency. Because `web-tree-sitter` loads that grammar via a dynamic `import()`, the `test:unit` script sets `NODE_OPTIONS=--experimental-vm-modules` so Jest's module VM can support it.
- Genuine external I/O — `pg` (`src/db/`), the GitHub REST API (`src/github/client.ts`), and orchestration layers that depend on either — is mocked with `jest.mock`.

### Performance budget tests (Lighthouse)

`npm run test:perf` (`scripts/perf-vitals.ts`) runs Lighthouse's performance category against the static pages — `/`, `/explore`, `/manifesto` — plus one real Lore Overview, `/lore/sindresorhus/globby`, under both the default mobile profile (simulated slow 4G + CPU throttling) and `--preset=desktop`, 3 runs each (`PERF_RUNS`), against both a target instance (`PERF_TARGET_URL`, default `http://localhost:3100`) and production (`PERF_PRODUCTION_URL`, default `https://repolore.app`), alternating the two on each run. It checks the target's medians of FCP, LCP, CLS, TBT (the lab stand-in for INP), Speed Index, and TTFB against each profile's budget (`BUDGETS` in `src/perf/compare-vitals.ts`, unit-tested) and reports a metric as over budget when its median exceeds it:

| Metric             | Desktop budget | Mobile budget |
| ------------------ | -------------- | ------------- |
| LCP                | 1.5 s          | 2.5 s         |
| FCP                | 0.5 s          | 1.8 s         |
| CLS                | 0.1            | 0.1           |
| TBT                | 150 ms         | 200 ms        |
| Speed Index        | 1.5 s          | 3.4 s         |
| TTFB (report-only) | 0.5 s          | 0.8 s         |

Desktop is the product's own budget; mobile (simulated slow 4G and a 4× CPU slowdown, where e.g. a 0.5 s FCP is unreachable even for production) uses Google's "good" Core Web Vitals/Lighthouse thresholds. Production is measured alongside only as context: its medians are shown next to the target's, and a breach notes when production is over the same budget too (so it predates the PR), but production never decides a breach. Breaches are advisory: they're listed (and, in CI, commented on the PR), but never make the run exit non-zero. TTFB is shown against its budget but never counted as a breach, since a CI-local server's response time reflects its distance to the database rather than the code. That Lore must already be analyzed in the target's database as well as production's (submit it on the home page, or `npm run seed -- <list-file>` with a list containing `sindresorhus/globby`; `npm run analyze-repo` doesn't persist): the warm-up request fails the run if either side renders the "not analyzed" panel rather than silently comparing a different page. Every request (Lighthouse's, via `--emulatedUserAgent`, and the warm-up's) appends a `RepoLorePerfBot` token to its user agent so `isCrawlerUserAgent` treats it as a crawler, and a perf run never pull-triggers a stale Lore's background re-analysis (ADR-0013/ADR-0017) on production or the instance under test. Every page is a cold, direct load. Cold by construction: the Lighthouse CLI launches Chrome through chrome-launcher, which gives each run a brand-new `mktemp -d` profile (so an empty disk cache) and deletes it afterwards, and Lighthouse resets storage before navigating. `coldLoadViolations` (`src/perf/compare-vitals.ts`) then fails the run if that storage reset was off, the navigation redirected (e.g. `http://`, `www.`, or a trailing slash) or ended on a different URL, or the document wasn't a 200; the warm-up request doesn't follow redirects either. It deliberately doesn't treat per-request cache hits as a warm load: with a fresh profile, a "disk"/"memory" hit is the page reusing something it already fetched in that same load. "Cold" means the browser: the warm-up still hits each URL once so a just-started server's first-request cost isn't measured against an always-warm production. Exit non-zero means a Lighthouse/setup error or a non-cold load, never a breach. Results land in `perf-report/report.{json,md}` and `perf-report/pr-comment.md` (gitignored). `npm run test:perf` handles the server itself: `.bin/with-prod-server` builds the current working tree, starts it on port 3100 (failing first if that port is taken), waits for `/api/health`, runs the check, and stops the server on any exit, including Ctrl-C. It shells out to the Lighthouse CLI (a devDependency) rather than its Node API, since `tsx`'s transform breaks the functions Lighthouse evaluates in the page; it uses an installed Chrome (`CHROME_PATH` to override). Not part of `npm test`.

### Continuous integration

`.github/workflows/verify.yml` runs on every pull request opened against `main` or `dev`, via GitHub Actions. A `changes` job lists the PR's files and runs the two real jobs only when something under `src/`, `public/`, `fixtures/`, `e2e/`, `scripts/`, the package manifests, `next.config.ts`, `jest.config.ts`, `postcss.config.mjs`, or the workflow itself changed; otherwise they're skipped. `verify` runs lint, build, and the Jest unit suite (uploading coverage to Codecov, plus a JUnit test-results report — `jest-junit` is enabled when `CI` is set and writes `test-results/junit.xml` — uploaded even when tests fail); `DATABASE_URL` is passed in from a repo secret of the same name, though the build doesn't connect to it. It's set only on the build and unit-test steps, not the whole job, so package lifecycle scripts run by `npm ci` never see it. `e2e` runs the full Playwright suite against a throwaway Postgres service container: `npm run migrate`, `npm run seed:e2e` (see "Functional/UI tests" above), then `npm run test:e2e`, uploading the Playwright report if it fails. Neither job needs `GITHUB_TOKEN`, and neither touches the shared database.

`.github/workflows/coverage.yml` runs on every push to `dev` or `main` (i.e. each merged PR): it runs `npm run test:unit:coverage` and uploads the report to Codecov, plus the JUnit test-results report (uploaded even when tests fail), so PR coverage from `verify` has a base-branch report to compare against. Pushes made with `GITHUB_TOKEN` (such as `release.yml`'s main → dev merge) don't trigger it.

`.github/workflows/react-doctor.yml` runs [React Doctor](https://github.com/millionco/react-doctor) on pull requests against `main` or `dev`, gated the same way by its own `changes` job, so it only runs when `src/` (or the workflow) changed.

`verify`, `e2e`, and `react-doctor` are required status checks on `main` and `dev`, set in a repository ruleset. That's why neither workflow uses a trigger-level `paths` filter: a filtered-out workflow never reports, and the PR would wait on it forever. A job skipped by its `if` counts as passing. The GitHub Actions app is a bypass actor on that ruleset, so `update-deps.yml` and `release.yml` can still push straight to `dev`.

`.github/workflows/perf.yml` is currently disabled (its job has `if: false`). When enabled, it runs `npm run test:perf` on pull requests against `main` or `dev` that touch `src/`, `public/`, dependencies, `next.config.ts`, or the perf script itself: `npm run test:perf` builds and starts the production server on the runner itself, then checks it against the budgets (with live production measured for context) using the runner's preinstalled Chrome. Breaches never fail the check (only errors and non-cold loads do): each is a warning annotation on the run, and the workflow posts one sticky PR comment (found by a `<!-- repolore-perf-check -->` marker, via `actions/github-script`) listing them with a pre-filled "create a ticket" issue link, updated on every later run and switched to an all-clear once they clear; nothing is posted while there's never been a breach, and fork PRs are skipped since their token can't comment. Needs `pull-requests: write` (the job's `permissions:` block). The budget table is added to the job summary and `perf-report/` is uploaded as an artifact either way. A `concurrency` group cancels a superseded run. `DATABASE_URL` is passed the same way as in `verify.yml`, scoped to the `npm run test:perf` step (`/` and `/explore` read Postgres per request).

`.github/workflows/update-deps.yml` updates dependencies weekly (Mondays 09:00 UTC, or manually via "Run workflow"), committing straight to `dev` with no PR. It checks out `dev`, bumps every dependency in `package.json` to its latest version with [`npm-check-updates`](https://github.com/raineorshine/npm-check-updates) — majors and exact pins (`next`, `react`, `prettier`, …) included, except `@types/node`, which is held to its current major so it keeps matching `.nvmrc` — then `npm install`s to refresh `package-lock.json`. It then runs `npx eslint` (no `--fix`), `npm run format:check` (`prettier --check .`), `npm run build`, and `npm run test:unit`. If all of them pass, it commits only `package.json` and `package-lock.json` as `github-actions[bot]` (the message lists each bump) and pushes to `dev`. If any step fails, nothing is pushed and the run goes red. Fixing the breakage (or pinning the offending package) is manual. If nothing is outdated, it exits without committing. Uses `GITHUB_TOKEN` with `contents: write`, so it assumes `dev` isn't branch-protected. A push made with `GITHUB_TOKEN` doesn't trigger other workflows, which is fine here since none run on push to `dev`. Playwright and Lighthouse aren't part of this gate. `DATABASE_URL` is passed the same way as in `verify.yml`, scoped to the build and unit-test steps, so neither `npm ci` nor the post-bump `npm install` runs lifecycle scripts with it set.

`.github/workflows/release.yml` runs on every push to `main`. When the pushed commit came from a merged `dev` → `main` pull request (looked up via the GitHub API) and isn't already tagged, it runs `npm run release -- --patch --target <sha> --yes`, creating the next patch tag (e.g. `v0.0.1` → `v0.0.2`) and a GitHub release with auto-generated notes on that exact commit. Any other push to `main` passes without releasing. Uses `GITHUB_TOKEN` with `contents: write` (plus `pull-requests: read`). Render deploys `main` only after this check passes (see "Deployment"), so the tag exists before the build reads it for the footer version. `verify.yml`'s checkouts use `fetch-depth: 0` for the same reason: a shallow clone has no tags, and the footer e2e spec expects the version. After a release it merges `main` back into `dev` and pushes, so the new tag is reachable from `dev`. Because `main` only ever receives squash merges, that merge is normally trivial. It fails, leaving `dev` untouched, only if `dev` changed the same lines between the PR merge and the release, and that merge then has to be resolved by hand.

`.github/workflows/nightly-release.yml` runs daily at 06:00 UTC (or manually via "Run workflow"). If `dev`'s tree differs from `main`'s, it reuses the open `dev` → `main` pull request or opens one (titled `chore(release): merge dev into main`, listing `dev`'s commits since the last back-merge). It then waits for that PR's checks and squash-merges it, pinned to the commit the checks ran on. Merging triggers `release.yml` above, so the result is a patch release, a Render deploy, and the back-merge into `dev`. A failing check leaves the PR open and fails the run. Verify and React Doctor always report on that PR, so a docs-only diff passes on skipped jobs rather than having no checks. Commits pushed to `dev` mid-run make the merge refuse, and the next run picks them up. It needs a `RELEASE_TOKEN` repository secret: a fine-grained personal access token for this repo with Contents and Pull requests read/write, plus Checks and Commit statuses read. `GITHUB_TOKEN` can't be used because PRs opened or merged with it don't trigger `verify.yml` or `release.yml`.

## Analyzing a real repository from the command line

`npm run analyze-repo` runs the fetch-extract-analyze path against any real public GitHub repository without touching the database — useful for quickly checking analyzer output on a new repo:

```
npm run analyze-repo -- https://github.com/sindresorhus/globby
```

This resolves the repository's default branch and HEAD commit, downloads and safely extracts its tarball into a temp directory (`src/acquisition/`), runs the same JS/TS extraction and derived-view logic used for local fixtures against it, prints Start Here / major areas / entry points / gaps, and always cleans up the temp directory afterward. Requires `GITHUB_TOKEN`. The real web flow (home page → `/lore/{owner}/{repo}`) additionally persists the result — see below.

`npm run analyze-python-repo` is the same thing for the Python analyzer:

```
npm run analyze-python-repo -- https://github.com/neubig/starter-repo
```

Neither script runs the language-detection dispatch that the real `/lore/{owner}/{repo}` flow does (ADR-0007) — each always runs its one named analyzer regardless of what the repository actually contains, so they're for checking a single analyzer's output in isolation, not for reproducing what a real submission would do.

## Seeding popular repositories

`npm run seed [-- <list-file>]` (`scripts/seed-repos.ts`) pre-analyzes the repositories listed in `scripts/seed-repos.txt` (one `owner/repo` per line, `#` comments allowed) — deliberately just six of the most-starred TypeScript/JavaScript repositories, matching the home page's `FEATURED_REPOS`, since the earlier ~50-repository list took too long and overloaded the production database so there are indexable Lore pages to share. It runs each one, sequentially, through the same `analyzeAndPersistRepository` path a home-page submission uses, skips any repository analyzed under a day ago or currently rate-limited, and prints a per-repository status plus a final tally. Operator-run by hand only — never scheduled (`docs/product/non-goals.md`); ADR-0013's pull-triggered refresh keeps seeded pages current from there. Requires `GITHUB_TOKEN` and `DATABASE_URL` (loads `.env.local` if present); point `DATABASE_URL` at Neon to seed production.

## Releases

Versions are git tags only (`vX.Y.Z`); `package.json`'s `version` isn't used. Merging `dev` into `main` patch-bumps automatically, and a nightly workflow does that merge whenever `dev` has unreleased changes (see "Continuous integration"). For a minor, major, or specific version, run `scripts/release.ts` (needs the `gh` CLI, authenticated with push access):

```bash
npm run release -- --minor            # or --major / --patch
npm run release -- --version 1.2.0    # explicit; must be newer than the latest tag
npm run release -- --minor --dry-run  # print the next tag only
```

It reads the latest tag from `origin` (not local tags), asks for confirmation (`--yes` skips it), and runs `gh release create <tag> --target main --generate-notes`, so GitHub creates the tag at `main`'s tip regardless of your local checkout (`--target <ref>` overrides). The version arithmetic lives in `src/lib/release-version.ts`. A manual release doesn't redeploy by itself: the footer shows the new tag from the next deploy of `main`.

## Database

`repos` and `analysis_runs` (ADR-0004, ADR-0005) are plain hand-written SQL files under `src/db/migrations/`, applied in filename order by `npm run migrate` (`scripts/migrate.ts`), which tracks what's already applied in a `schema_migrations` table — no migration framework yet, since a couple of tables don't justify one. `analysis_runs` is keyed by `(repo_id, commit_sha, analyzer_version)` (ADR-0005) and stores the full serialized `Lore` (`src/lore/model.ts`) as `result jsonb` on success, or `error_message` on failure; `status` matches `AnalysisSnapshot['status']` (`completed`/`partial`/`failed`) exactly. Requires `DATABASE_URL` (see .env.example); `docker compose up -d db` runs a matching local Postgres (Postgres 18, data in the `repolore-db-data-18` volume mounted at `/var/lib/postgresql`, the layout 18+ images require). Upgrading from the earlier Postgres 17 setup: the old `repolore-db-data` volume isn't read by 18, so `pg_dumpall` it from a temporary `postgres:17-alpine` container first and restore the dump with `psql -d postgres` into the new one; the old volume is left in place until you `docker volume rm` it.

Submitting the home page's form (`src/app/actions.ts`) calls `analyzeAndPersistRepository` (`src/analysis/analyze-and-persist.ts`), which resolves the repo's HEAD and GitHub's language breakdown, decides which analyzer(s) to run (ADR-0007's dispatch — `src/analysis/dispatch/detect-languages.ts`), short-circuits if that exact commit+analyzer-set has already been analyzed (ADR-0005 idempotency — no redundant tarball fetch on repeat submissions), and otherwise acquires the source once, runs every selected analyzer, enriches each extracted external dependency with a registry description (`src/registry/`, ADR-0011 — bounded, non-fatal, no `GITHUB_TOKEN`/auth needed since the npm and PyPI registries are public), merges everything into one `Lore`, persists it, and redirects to `/lore/{owner}/{repo}`. Every outcome — success, partial, or failed (including "no supported language was detected") — is persisted and rendered there; nothing is silently dropped.

**One Lore per repository, under GitHub's canonical name (GitHub issue #43).** A repository can be reached by more than one spelling: the old name of a renamed or transferred repository (`facebook/react` is now `react/react`; GitHub redirects the old name), or different letter case (GitHub matches case-insensitively, but `repos`' `UNIQUE (owner, name)` doesn't). `resolveRepositoryHead` (`src/github/client.ts`) returns GitHub's canonical `owner`/`repo` from the response body, and `analyzeAndPersistRepository` persists the run under that identity with `upsertCanonicalRepo` (`src/db/repos.ts`). That function adopts an existing case-variant row and re-spells it, keeping its runs, history, and rate-limit state, instead of inserting a duplicate. A repository already stored under any case is rate-limited before any GitHub call. A never-seen one is rate-limited as soon as resolution names its canonical row. Submissions redirect to the canonical `/lore/{owner}/{repo}`, and so does "Re-analyze" when the canonical name differs from the page's. A `/lore/{owner}/{repo}/**` page with no run under that exact spelling does a DB-only, case-insensitive lookup (`findRepoIgnoringCase`, via `src/lib/redirect-to-stored-spelling.ts`) and permanently (308) redirects to the stored spelling, keeping the subpage. A page view never calls GitHub (ADR-0017), so an old name that was never submitted isn't detected there. Submitting it resolves and redirects as above.

Rows created under a non-canonical name before this fix are not merged automatically. To clean them up by hand, first list candidates: `SELECT id, owner, name FROM repos ORDER BY lower(name), lower(owner);`. Then, for a renamed repository whose canonical row already has runs (for example `facebook/react` alongside `react/react`), delete the old row with `DELETE FROM repos WHERE owner = 'facebook' AND name = 'react';`. This cascades its `analysis_runs` and `history_entries`. Case-only duplicates collapse on their next analysis. A unique index on `(lower(owner), lower(name))` is deliberately not added yet. It would fail to apply wherever case duplicates already exist.

The "Re-analyze" button on `/lore/{owner}/{repo}` and a pull-triggered background re-analysis (ADR-0013, see below) both go through one shared function, `reanalyzeAndRefreshHistory` (`src/analysis/reanalyze-and-refresh-history.ts`): it calls `analyzeAndPersistRepository`, rate-limited per repository (`repos.last_analysis_requested_at`, `src/analysis/reanalysis-rate-limit.ts`, one attempt per 60 seconds by default) so a rapid click — or a burst of simultaneous visitors — can't repeatedly burn through the shared GitHub token's rate limit even when the analysis itself short-circuits on an unchanged commit; and, only when that actually produces a new run (not the idempotent short-circuit), also recomputes and re-caches the History page's `history_entries` row, so History doesn't keep showing entries computed against the previous analysis until someone separately clicks "Refresh history" (GitHub issue #13) — this recompute deliberately bypasses History's own 60-second cooldown (`src/history/history-rate-limit.ts`), since it's a direct consequence of an already-rate-limited re-analysis rather than a manual refresh click, and a failure here is logged rather than surfaced, since the re-analysis itself still succeeded. The manual button (`src/app/actions.ts`'s `reanalyzeRepository`) additionally revalidates `/lore/{owner}/{repo}` and, when History was actually refreshed, `/lore/{owner}/{repo}/history`.

There's no _headless_ scheduled refresh (cron, webhooks, polling with no visitor — see `docs/product/non-goals.md`), but a repository whose latest analysis is over a day old gets a bounded, pull-triggered exception (ADR-0013): visiting any `/lore/{owner}/{repo}/**` page for it schedules `reanalyzeAndRefreshHistory` to run in the background, after that visitor's response is already sent (`scheduleBackgroundReanalysisIfStale` in `src/analysis/background-reanalysis.ts`, called from the route's shared `layout.tsx`, via `next/server`'s `after()`) — the visitor isn't slowed by a possible tarball fetch/extraction, and the same per-repo rate limit above means simultaneous visitors to a popular stale repo don't each start a redundant attempt. The Overview page also shows a dismissible notice once the latest analysis is a day old (`src/components/lore-shell/StaleAnalysisCard.tsx`, gated by `isAnalysisStale` in `src/helpers/`) describing that background check, with the manual "Re-analyze" button still available for anyone who doesn't want to wait for it or a reload.

## Deployment

Live at [https://repolore.app](https://repolore.app). Hosted on [Render](https://render.com) (Pro plan web service — a real long-running Node process per ADR-0001, not a serverless function) with [Neon](https://neon.tech) (free Postgres) — chosen over Fly.io/Railway (both dropped their free tiers) and Render's own Postgres (free databases there expire after 30 days).

`render.yaml` at the repo root is a Render [Blueprint](https://render.com/docs/blueprint-spec): `npm install && npm run build` to build, `npm run start` to run, `/api/health` as the health check path. `GITHUB_TOKEN` and `DATABASE_URL` are marked `sync: false`, so Render prompts for their real values in its dashboard at blueprint-creation time rather than reading them from this file — they are never committed. `NEXT_PUBLIC_SITE_URL` is set to `https://repolore.app` directly in `render.yaml`, since it isn't a secret.

First deploy, one-time setup:

1. Create a free [Neon](https://neon.tech) project and copy its pooled connection string (includes `?sslmode=require`, which `pg` honors automatically — no code change needed).
2. Apply the schema to it: `DATABASE_URL=<neon-connection-string> npm run migrate`.
3. Create a free [Render](https://render.com) account, connect it to this GitHub repo, and deploy `render.yaml` as a Blueprint. When prompted, paste the real `GITHUB_TOKEN` (see `.env.example`) and the Neon connection string as `DATABASE_URL`.

The service runs on Render's Pro plan, so it stays up instead of spinning down after 15 minutes idle the way the free tier did (no 30–60s cold start for the first visitor). The custom domain `repolore.app` is attached in the Render dashboard, and `render.yaml` sets `NEXT_PUBLIC_SITE_URL=https://repolore.app` so canonical/Open Graph/Twitter/sitemap/badge URLs use it rather than Render's own `RENDER_EXTERNAL_URL` (see `.env.example`). Subsequent deploys happen automatically on push to `main`; `render.yaml` sets `autoDeployTrigger: checksPass`, so Render waits for `main`'s checks — including the Release workflow's tag — before building, and the footer shows the new version; re-run `npm run migrate` against the Neon `DATABASE_URL` after any change to `src/db/migrations/`.
