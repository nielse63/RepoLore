# ADR-0016: React-flow pan/zoom for the area dependency diagram amends ADR-0009's "non-interactive" rule

## Status

Accepted

## Context

ADR-0009 built the area dependency diagram as static, server-rendered SVG and explicitly rejected `react-flow` by name as its rendering library: _"their entire value proposition is interactivity (pan/zoom/drag/minimap/controls), which stays explicitly out of scope; installing an interactive-first library invites 'since it's already there' interactivity creep, and it's a heavier, faster-moving dependency than this problem justifies."_

`AreaDependencyDiagram.tsx`'s own layout clamps the rendered SVG's height to `Math.min(Math.max(layout.height + 80, 320), 600)` — a diagram whose dagre-computed layout is taller than 600px is only ever partially visible, with no way to see the rest. After using the diagram day-to-day against real repositories, the product owner found this a real limitation for repositories with enough Major Areas to produce a tall diagram, and — on branch `spike/reactflow-area-diagram` — explored replacing the static SVG renderer with `@xyflow/react` (react-flow) specifically for its pan/zoom/`fitView` navigation. Having used the result, the product owner chose to keep it and asked for it to be made production-ready rather than reverted, which requires this ADR: shipping react-flow at all is a direct reversal of ADR-0009's rejection, and needs the same deliberate, documented treatment ADR-0009 itself required before its own exception was accepted.

A `product-scope-guardian` review, run before this ADR was written, found that keeping react-flow here is defensible, but only in a narrow slice: ADR-0009's rejection targeted _unbounded_ interactivity risk on what it treated as an unbounded-feeling library, not a version where dagre remains the sole layout authority and react-flow is used purely as a renderer for pan/zoom on a diagram that is still capped, still area-level, and still read-only. The review found the branch's code at review time exceeded that narrow slice — react-flow's full default `<Controls>`/`<Background>` shipped with no capability flags disabled (`nodesDraggable`, `nodesConnectable`, `elementsSelectable` all default `true`) — and required the guardrails in Decision items 3–4 below before this ADR could record the exception as scoped rather than unbounded.

## Decision

1. **`@xyflow/react` (react-flow) replaces static server-rendered SVG as the area dependency diagram's renderer.** `AreaDependencyDiagram.tsx` becomes a client component (`"use client"`), taking plain `owner`/`repo`/`commitSha` data instead of an `areaUrl` callback prop, since a client component cannot accept a function prop from the server components that embed it (Overview, Architecture, Systems, and each Systems subview).
2. **Dagre remains the sole layout authority.** `deriveProductionAreaDiagramLayout` (`@dagrejs/dagre`, unchanged from ADR-0009) still computes every node position and edge route; react-flow is a rendering surface only and never recomputes or overrides that layout.
3. **Explicitly allowed:** pan (drag on empty background), zoom (wheel, pinch, and the `Controls` panel's buttons), `fitView` on load, react-flow's default `<Controls>` and `<Background>`.
4. **Explicitly disabled, as literal props rather than left at react-flow's defaults:** `nodesDraggable={false}`, `nodesConnectable={false}`, `elementsSelectable={false}`. No `<MiniMap>`. No multi-select, no click-to-filter or click-to-highlight, no edge creation or editing. `<Controls showInteractive={false}>` additionally hides react-flow's built-in "Toggle Interactivity" button — found during verification of this ADR's guardrails — since its sole purpose is to re-enable the three capabilities just disabled (the explicit props above already win over it even when clicked, verified by simulating the click-then-drag sequence, but a control whose only function is to undo a deliberate guardrail shouldn't be offered at all). This is the guardian review's required guardrail against exactly the "since it's already there" creep ADR-0009 warned about.
5. **Every other ADR-0009 guardrail carries forward unchanged:** the `MAX_DIAGRAM_AREAS = 30` node-count ceiling and its table-only fallback, area-level-only scope (file-level `Relationship` edges remain undiagrammed), no cycle-detection callouts, and ADR-0009's own item 7 — any further extension (file-level diagrams, drag, minimap, multi-select, click-to-filter) needs its own ADR and `product-scope-guardian` review.
6. **This ADR does not reopen or extend ADR-0012's rejection of react-flow for the Data Flow call graph.** That feature keeps its dagre-only, non-react-flow rendering unchanged — see Rationale for why the two are distinguished rather than treated as one precedent.
7. **`@xyflow/react` stays on this project's normal caret-range convention** (`^12.11.6`), matching every other non-framework dependency in `package.json`, including `@dagrejs/dagre` itself — the committed lockfile already pins the exact resolved version for reproducible installs, which is what a lockfile is for; this ADR does not introduce a one-off exact-pin exception for a single package.

## Rationale

**Why this narrows ADR-0009's rule rather than repeals it.** ADR-0009's rejection reasoning was written against react-flow's _default_ posture — a general-purpose graph editor where interactivity is the whole point and every capability ships on by default. What's shipping here is materially narrower: the diagram is still capped at 30 nodes, still laid out exclusively by dagre, still read-only in every way that matters (no editing, no persistence of any view state), and react-flow's node/edge editing surface is switched off at the prop level, not merely left unused by convention. The single capability added — pan/zoom — solves a concrete, disclosed limitation (the 600px height clamp) that ADR-0009's static SVG had no answer for beyond "the diagram is cut off." That is a scoped amendment, not the wholesale reversal ADR-0009's own item 7 anticipated needing a fresh ADR for.

**Why ADR-0012's call-graph rejection isn't reopened by this.** ADR-0012 rejected react-flow using similar "always small, always capped" language, which could read as identical to this diagram's case. The distinction is real but is a judgment call, not a clean principle: the area diagram is a single, fixed view of a repository's entire (capped) area graph at once, where a diagram taller than the viewport is a recurring, disclosed problem pan/zoom directly solves. The call graph instead renders one function's bounded local neighborhood at a time, recomputed fresh and re-centered on every focus change (ADR-0012, Decision item 5) — a view that is ephemeral and already scoped to fit, so pan/zoom solves nothing there that re-focusing doesn't already handle more directly. Both ADRs' choices are accepted as correct for their own feature; this ADR does not claim the reasoning generalizes any further than these two named cases.

**Bundle-size consequence, disclosed rather than absorbed silently.** ADR-0009's choice of dagre specifically relied on it running server-side only, "never included in the client JS bundle" — the diagram itself was static SVG, so no graph library ever reached the browser. Because pan/zoom is inherently a client-side interaction, that property no longer holds: `@xyflow/react` now ships to the browser on every page that embeds `AreaDependencyDiagram` (Overview, Architecture, Systems, and each Systems subview). This is a real, new cost ADR-0009 didn't have to weigh, accepted knowingly here rather than glossed over.

**Lazy-loading considered, not implemented this pass.** The guardian review recommended lazy-loading the client component (`next/dynamic`, deferring `@xyflow/react`'s JS until the diagram is actually rendered) to offset the bundle-size consequence above. This project's `next` dependency is pinned to a version with breaking changes from the publicly documented API (see this repo's root `CLAUDE.md`), and this pass's environment could not read that version's own bundled docs to verify its `next/dynamic` behavior before shipping code against it. Rather than guess at an unverified API in the framework's own code-splitting primitive, lazy-loading is deferred as a disclosed follow-up (see Consequences) instead of attempted speculatively.

## Consequences

- `AreaDependencyDiagram.tsx` is a client component; `@xyflow/react`'s runtime ships to the browser on every page that embeds it, a departure from ADR-0009's "the graph library never reaches the client" property (see Rationale).
- `docs/product/non-goals.md`'s "interactive dependency graphs" bullet is amended to describe the area diagram's scope as pan/zoom/`fitView` only, referencing this ADR, alongside its existing ADR-0009/ADR-0012 references.
- `README.md`'s ADR-0009 paragraph is updated to describe the diagram as client-rendered with react-flow (pan/zoom/`fitView` only; dragging, connecting, and selection explicitly disabled) rather than static server-rendered SVG.
- New Playwright coverage (`e2e/area-dependency-diagram.spec.ts`) asserts the diagram renders as a react-flow canvas with real area nodes and edges, that zoom controls work, and — as a regression guard for Decision item 4 — that attempting to drag a node does not move it.
- Lazy-loading the diagram's client bundle via `next/dynamic` is a disclosed, deferred follow-up (see Rationale) — not implemented in this pass.
- No `Lore` shape or analyzer-version change results from this ADR — it is presentation-layer only. (A separate, unrelated area-relationship-granularity fix landed on the same branch; see `docs/architecture/implementation-plan.md`'s dated entry for that work, which did require an analyzer-version bump.)
- Every repository already analyzed is unaffected; nothing about how a diagram is fetched, gated, or fell back to a table changes — only how a diagram that does render is drawn and navigated.

## Alternatives considered

**Keep the static SVG, accept the 600px cutoff as a known limitation.** Rejected — the product owner used the react-flow version directly and found pan/zoom a real improvement for repositories with enough Major Areas to exceed the fixed viewport, and asked for it to be kept rather than reverted.

**Add manual pan/zoom to the existing hand-rolled SVG rendering, without a graph-rendering dependency.** Considered and rejected for the same reasoning ADR-0009 already used to choose dagre over a hand-rolled layout algorithm: correctly handling wheel/pinch/touch/drag panning and zooming, and keeping it correct against arbitrary real-world usage, is real ongoing maintenance work for a solo maintainer at 5–8 hrs/week. If a graph-rendering dependency is going to be used at all, using the one already explored and validated on this branch is the better maintenance bet than a bespoke interaction layer maintained alongside it.

**Enable more of react-flow's built-in interactivity now that it's installed** (drag-to-reposition nodes, a `<MiniMap>`, multi-select, click-to-filter). Rejected by the `product-scope-guardian` review — exactly the "since it's already there" creep ADR-0009 warned about. None of these were requested, none solve a disclosed problem the way pan/zoom solves the height-clamp issue, and each would need its own ADR and review per Decision item 5.
