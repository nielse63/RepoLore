# ADR-0011: Real Dependencies page — new external-dependency extraction, plus two deliberate overrides of a scope-guardian review

## Status

Accepted

## Context

`/lore/{owner}/{repo}/dependencies` (`src/app/lore/[owner]/[repo]/dependencies/page.tsx`) previously rendered entirely hardcoded example content (`DEPENDENCIES` in `src/lib/fixtures/payments-service.ts`), matching `docs/designs/dependencies.png`'s mockup: a searchable table of dependencies (name, purpose, used-by services, version, evidence count) with a right rail showing detail, "used by," and evidence on row click, across "External" and "Internal" tabs (the mockup's third "Packages"-only tab and its filter dropdowns/AI-insight callout were never built and remain out of scope here).

**Unlike ADR-0008 (Architecture), this page needs genuinely new analyzer capability, not just re-presentation of existing `Lore`-model data.** Before this change, `src/lore/model.ts` had no concept of an external/third-party dependency at all. JS/TS's `extract-project.ts` read `package.json`'s dependency fields only to detect a UI-framework signal for `project.kind` inference, and `imports.ts` explicitly discarded bare import specifiers ("external packages ... intentionally not recorded"). Python's `project-config.ts` read `pyproject.toml`/`setup.cfg`/`setup.py` only for project name and console-script entry points, never dependency declarations, and `imports.ts` silently treated any unresolved absolute import as external/stdlib with no record kept.

A `product-scope-guardian` review, run before this ADR (see the implementation-plan session log), evaluated a seven-point draft proposal against mission alignment, MVP necessity, maintenance cost, operational risk, and simpler alternatives. It recommended: build the deterministic manifest-parsing and import-matching extraction; reuse the existing area-to-area relationship data (already built for Architecture) for the Internal tab now, at near-zero cost; but **reject** a per-dependency description (no deterministic source exists in the analyzed repository itself) and **reject** cosmetic per-dependency type icons (an open-ended package-name keyword list with no natural stopping point — the same failure mode ADR-0008 rejected for infrastructure detection).

**The product owner heard both recommendations and explicitly overrode them**, choosing a live registry description lookup and a bounded type-icon keyword list anyway. This ADR records those two overrides and the guardrails applied to keep each bounded, following ADR-0010's precedent for documenting a deliberate override rather than silently deviating from a review's advice.

## Decision

1. **New `ExternalDependency` entity** in `src/lore/model.ts` (id, projectId, name, declared version/spec, scope, registry, optional description/descriptionSource, evidence, gaps) and `Lore.externalDependencies: ExternalDependency[]`. `collectEvidence` includes it, so evidence-coverage figures elsewhere in the app grow to reflect it.
2. **JS/TS extraction** (`src/analysis/js-ts/external-dependencies.ts`): declares one entry per `package.json` `dependencies`/`devDependencies`/`peerDependencies`/`optionalDependencies` field (`detected`, from the manifest field itself). `imports.ts`'s previously-discarded bare specifiers are now returned as `ExternalReference[]` and matched to a declared package name by exact prefix (`@scope/pkg/sub` → `@scope/pkg`; `pkg/sub` → `pkg`); a match is `detected` usage evidence, since the match is unambiguous. A specifier matching nothing declared is left unrecorded, consistent with the existing precedent for asset imports and Node builtins.
3. **Python extraction** (`src/analysis/python/external-dependencies.ts`): `project-config.ts` now also reads PEP 621's `[project.dependencies]`/`[project.optional-dependencies]` and `[tool.poetry.dependencies]`/`[tool.poetry.dev-dependencies]` (the modern per-group `[tool.poetry.group.*.dependencies]` syntax is not read — a disclosed, narrow scope decision, the same shape as this file's existing `setup.cfg` console-script limitation). `imports.ts`'s previously-silent unresolved absolute imports are now returned as `ExternalReference[]` (top-level module name) and matched against declared names by case/punctuation-insensitive normalization — necessarily `inferred`, never `detected`, since Python import names frequently differ from their PyPI distribution name (`PyYAML`→`yaml`, `Pillow`→`PIL`). A declared dependency with no matched import gets an honest `unknown` gap reading "no usage detected... doesn't necessarily mean it's unused" — the heuristic can't rule out real usage under a differently-named import, so it must not be phrased as a stronger claim than the evidence supports.
4. **No lockfile parsing.** `declaredVersion` is always the manifest's own version range/spec, never a lockfile-resolved exact version. The mockup's "Direct"/"Transitive" scope distinction is not reproduced (transitive dependencies require full graph resolution); real scope values are Direct/Dev/Peer/Optional.
5. **Override 1 — live registry description lookup** (`src/registry/npm.ts`, `pypi.ts`, `enrich-descriptions.ts`), called once per analysis run from `analyze-and-persist.ts` between extraction and `buildLore`, deliberately kept out of the language extractors themselves so extraction stays local/deterministic and the one place that talks to an external network service can be reasoned about, capped, and failed independently. Bounded on three axes: a 5-second per-request timeout (`AbortSignal.timeout`), a concurrency cap of 5, and a hard cap of 100 dependencies enriched per run — a run with more than that gets an honest "lookup skipped" gap for the remainder rather than an unbounded fetch fan-out. Any failure (timeout, network error, non-2xx, missing field) is non-fatal: the dependency keeps no description and gets an honest `unknown` gap, never a thrown error. No cross-repo cache exists in v1 — kept out to keep this reversible and minimal; worth adding if it proves slow or rate-limited in practice. Description text is kept out of the Detected/Inferred certainty system entirely (it's package metadata from an external registry, not an analysis conclusion about the repository) and disclosed in the UI with a "via npm registry"/"via PyPI registry" caption.
6. **Override 2 — cosmetic type icon** (`src/lib/dependency-category.ts`): a small, fixed keyword-to-category map (network, database, testing, validation, tooling, framework) matched by exact package name, generic icon fallback for anything unmatched. Purely a UI decoration — not a model field, not evidence, no certainty label. Deliberately closed rather than pattern-matched, so it can't silently grow into an open-ended classification claim.
7. **Internal tab**: reuses `deriveAreaRelationships` (ADR-0008) exactly as the Architecture page does — same table shape (Area / Depends on / Certainty), no new analyzer work, no diagram (the area-dependency diagram, ADR-0009, is not duplicated onto this page in this round, to keep the change bounded).
8. **Backward compatibility for already-persisted runs**: `src/db/analysis-runs.ts`'s `mapRow` now normalizes `result.externalDependencies` to `[]` when reading a pre-existing row whose stored JSON predates this field, at the single DB read boundary rather than in every consumer. Without this, every repository analyzed before this change would crash the Dependencies page (`undefined` where an array was expected) until manually re-analyzed.
9. **Analyzer version bump** (ADR-0005): `JS_TS_ANALYZER_VERSION` `js-ts-v5` → `js-ts-v6`, `PYTHON_ANALYZER_VERSION` `python-v3` → `python-v4` — the `Lore` shape materially changed for both languages.

## Rationale

Points 2–4 pass the same bar ADR-0008 used to reject infrastructure/data-store detection: unlike "labeling Redis as a cache/queue" (an inferred _usage_ claim the analyzer can't justify), reading a manifest's own declared dependency list is a direct field read, and matching an import specifier to that declared name is a bounded, mechanical operation with a natural stopping point — there's no equivalent of "which of dozens of possible infrastructure technologies is this" here.

The two overrides were rejected by the scope-guardian review for the same reason ADR-0008 rejected infra detection and expanded framework detection: no natural stopping point, and (for the type icon) a decorative feature nonetheless implying categorization confidence it doesn't carry. The product owner's override is recorded, not silently substituted, per ADR-0010's established pattern — future reviewers should not read this ADR's existence as a signal that scope-guardian recommendations can be routinely overridden without discussion; each override here was a specific, considered call, made with the tradeoffs explicit (see the design conversation preceding this ADR).

## Alternatives considered

**Omit the description for v1** (the scope-guardian's actual recommendation) — the safer default, with zero new external dependency and zero fabrication risk. Available again if the registry integration's maintenance cost (rate limits, staleness, registry outages) proves too high in practice; the bounded/non-fatal design in point 5 was chosen specifically to make that reversal cheap if needed.

**A small curated description map** for common packages — rejected for the same "no natural stopping point" reason ADR-0008 rejected infra detection: it doesn't scale past the packages someone remembered to hand-write, and silently produces uneven coverage.

**Open-ended package-name pattern matching for the type icon** (e.g. any name containing "db", "sql", "http") — rejected in favor of an exact, closed keyword list: substring matching risks false positives on unrelated package names and has no natural stopping point either.

## Consequences

- New application code: `src/lore/model.ts` additions; `src/analysis/js-ts/external-dependencies.ts`, `src/analysis/python/external-dependencies.ts`; extensions to both languages' `imports.ts`/`extract-project.ts` and Python's `project-config.ts`; `src/registry/` (`npm.ts`, `pypi.ts`, `enrich-descriptions.ts`); `src/lib/dependency-category.ts`; `src/components/lore-shell/DependenciesContent.tsx`; the rewritten `dependencies/page.tsx`; the `mapRow` backward-compatibility normalization in `src/db/analysis-runs.ts`.
- `src/lib/fixtures/payments-service.ts`'s `DEPENDENCIES` export becomes unused by the real page (left in place, matching ADR-0008/ADR-0010 precedent).
- This is now the second feature (after ADR-0010's GitHub commit history) that makes live external network calls proportional to repository content during analysis — up to 100 registry lookups per run, capped and non-fatal, worth monitoring once deployed alongside History's GitHub API volume.
- Every repository analyzed before this change needs a manual re-analysis before its Dependencies page shows real data; until then it shows an honest "no external dependencies were detected" rather than crashing, per point 8.
- The rejected/deferred pieces (lockfile-resolved exact versions, a cross-repo description cache, the mockup's third "Packages" tab and filter dropdowns, an AI-generated insight callout, an Internal-tab diagram) remain available as later, independently-scoped work.
