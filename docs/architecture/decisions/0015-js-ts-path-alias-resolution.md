# ADR-0015: JS/TS path-alias resolution across tsconfig/jsconfig, package.json, and common bundler/framework configs

## Status

Accepted

## Context

ADR-0003 scoped the JS/TS analyzer to syntactic import resolution: relative specifiers (`./`, `../`) resolve to a discovered source file, but any alias-shaped specifier (heuristically, anything starting with `@/`) was reported as an honest `unsupported` Gap. ADR-0003's own "Consequences" section flagged this as deferred work — "additional (non-type-checker) alias-resolution logic reading `tsconfig.json` `paths` directly" — but it sat unaddressed from implementation session 4/6 onward, measurably shortening Start Here/dependency-chain output on alias-heavy repositories (`fixtures/ts-react-app`'s own `tsconfig.json` `"@/*": ["src/*"]` is the canonical repro).

GitHub issue #24 (`priority: high`) asks for real alias resolution across up to ten possible config sources: `tsconfig.json`, `jsconfig.json`, `package.json`'s `imports` field, `vite.config.*`, `webpack.config.*`, `.babelrc`/`babel.config.*`, `next.config.*`, `nuxt.config.*`, `rollup.config.js`, `rsbuild.config.ts`.

The critical constraint is `docs/product/non-goals.md`'s explicit exclusion of **executing code from analyzed repositories**. `tsconfig.json`, `jsconfig.json`, and `package.json` are plain JSON (JSONC for the first two) and safe to parse directly. The remaining seven sources are JS/TS files whose real configuration is normally only knowable by executing them (they can be functions, read environment variables, spread variables, etc.) — executing arbitrary repository code to obtain it was rejected outright as out of scope.

## Decision

1. **New module `src/analysis/js-ts/project-config.ts`** reads and merges path-alias configuration from every supported source present in a repository, mirroring the existing Python analog (`src/analysis/python/project-config.ts`): read known config files, never execute them, return a plain data structure (`PathAlias[]` plus any `Gap`s).
2. **JSON-shaped sources are parsed directly**: `tsconfig.json`/`jsconfig.json` via `ts-morph`'s re-exported `ts` namespace (`ts.readConfigFile` + `ts.parseJsonConfigFileContent`, already a dependency — no new package), which resolves `extends` chains and tolerates comments/trailing commas the way `tsc`/VS Code do; `package.json`'s `imports` field via plain `JSON.parse`.
3. **The seven bundler/framework/babel config files are parsed syntactically via `ts-morph`'s AST, never executed.** Only literal alias patterns are extracted: a plain object of `string -> string`, an array of `{find, replacement}` objects (Rollup's `@rollup/plugin-alias`, Vite's array alias form), or a `path.resolve(...)`/`path.join(...)` call whose string-literal arguments are joined (non-literal arguments like `__dirname` are ignored — these files live at the repo root in the overwhelming majority of real projects, so using the config file's own directory as the base covers that case without modeling `__dirname`/`import.meta.url` semantics). A config that computes its object via a function (e.g. `defineConfig((env) => ({...}))`) is out of scope, since nothing here evaluates functions; any alias-shaped import in that repo falls through to the existing "looks like an alias, unsupported" Gap. A recognized alias key whose _value_ is computed (a variable reference, spread, ternary, or unrecognized call) is likewise left unresolved and reported as an `unknown` Gap rather than guessed.
4. **Fixed precedence order** when the same alias key is declared in more than one source (highest first — whatever actually resolves modules at build/runtime outranks a declaration-only config, which outranks Node's narrower subpath-import mechanism): `vite.config.*` → `webpack.config.*` → `rsbuild.config.*` → `rollup.config.*` → `nuxt.config.*` → `next.config.*` → babel config → `tsconfig.json` (preferred over `jsconfig.json` when both exist) → `jsconfig.json` → `package.json` `imports`. A losing declaration is simply dropped, not reported as a Gap — this is a merge decision, not an analysis limitation. Every resolved alias's evidence description names the winning config file (and, where applicable, its config key) for traceability, per the mission's evidence-hierarchy principle.
5. **`next.config.*` gets one narrow, explicit pattern**: Next.js has no first-class alias option (it inherits tsconfig `paths` automatically) — the only common way to add one is mutating `config.resolve.alias` inside a `webpack(config, ...) {...}` function (covering both the object-literal method shorthand and a `webpack: function(...) {}`/arrow-function property). Anything else is left to tsconfig `paths`, which Next apps overwhelmingly rely on already.
6. **`module-resolution.ts`'s `buildModuleResolutionIndex`** gains `rootDir` and an optional `aliases: PathAlias[]` parameter. A non-relative specifier is matched against the longest-matching configured alias (`exact` match type for a webpack-style trailing-`$` alias or a non-wildcard tsconfig/package.json key; `prefix` otherwise) and, on a match, resolved through the same extension/index-file candidate logic already used for relative specifiers. `imports.ts` attempts this resolution for every non-relative specifier; on success it records a normal `depends-on` Relationship (citing the winning alias source in its evidence); on failure, an alias-shaped specifier (the existing `looksLikePathAlias` `@/`-heuristic) still gets an honest `unsupported` Gap, now clarified to say no matching configuration resolved it.
7. **Analyzer version bump** (ADR-0005): `JS_TS_ANALYZER_VERSION` `js-ts-v9` → `js-ts-v10` — previously-`unsupported`-gapped aliased imports now resolve to real Relationships for many repositories, materially changing extraction output.

## Rationale

Reading JSON directly and parsing JS/TS configs syntactically (rather than executing them) keeps this feature inside ADR-0003's existing syntactic-only philosophy and inside the product's "never execute analyzed-repository code" boundary, at zero new npm dependencies. The generic literal-object/array walker, reused across all seven bundler/framework/babel sources, keeps the ten-source breadth the issue asks for from becoming ten bespoke parsers — each source only needs to say _where_ to look for an alias-bearing node; the resolution of what that node's values mean is shared. The fixed precedence order matches how these tools actually behave in practice: a bundler config is what really resolves a module at build time, so it should win over a type-checker-only declaration, which in turn is more general-purpose than Node's `imports` map.

## Alternatives considered

**Constructing a type-checked ts-morph `Program` via `tsConfigFilePath`** — rejected, since it would resolve tsconfig `paths` "for free" but only for that one source, contradicts ADR-0003's explicit rejection of a type-checked `Program` for v1, and does nothing for the other nine sources issue #24 asks for.

**Executing config files in a sandboxed subprocess** to get their real resolved values — rejected outright per `docs/product/non-goals.md`'s "executing code from analyzed repositories" exclusion; the maintenance and security surface of sandboxing arbitrary repository code is exactly the kind of cost this product is built to avoid.

**Limiting v1 to JSON-only sources** (tsconfig/jsconfig/package.json) — the safer, zero-ambiguity option and the one ADR-0003 originally anticipated; not chosen because the product owner explicitly asked for best-effort coverage of all ten sources issue #24 lists, accepting that computed/dynamic bundler-config aliases remain disclosed Gaps rather than resolved.

## Consequences

- New application code: `src/analysis/js-ts/project-config.ts` and its spec; extensions to `module-resolution.ts`, `imports.ts`, `extract-project.ts`, and their specs.
- Computed/dynamic alias targets, and any config shape none of the recognized patterns matches (a function-computed `defineConfig`, a webpack config mutating `resolve.alias` some other way, a RegExp `find` in Vite's array form), remain honest Gaps rather than resolved or guessed — a disclosed, narrower-than-execution capability, not a silent gap in coverage.
- Every repository analyzed before this change should be re-analyzed to pick up newly-resolvable aliased imports; the analyzer version bump (point 7) means a fresh run is produced rather than silently reusing a stale one.
- Still no `tsConfigFilePath`-driven type-checked `Program` — this is additive to `module-resolution.ts`, not a rewrite of the syntactic-only approach ADR-0003 established.
