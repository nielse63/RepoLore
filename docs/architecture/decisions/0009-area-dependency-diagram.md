# ADR-0009: A static, non-interactive, area-level dependency diagram is a scoped exception to ADR-0008's "no diagram" decision

## Status

Accepted

## Context

The Overview page's "Direct Relationships" section (`OverviewContent.tsx`) rendered every raw file-to-file `depends-on` edge produced by the JS/TS import extractor as a flat table — potentially hundreds of rows for a real repository, with almost every "Kind" cell reading literally `depends-on`. The product owner flagged this as clunky and uninformative for the app's core orientation-confidence promise, and asked to explore a visual, graph-style presentation similar to how tools like Madge, skott, dependency-cruiser, and dpdm display module relationships.

ADR-0008 (session 19) already evaluated and rejected diagram rendering for the Architecture page's first real version. Its "Alternatives considered" section specifically weighed a **"Static area-only diagram"** middle ground and rejected it: _"no diagram library exists yet, `StructuralArea` has no layer/tier concept to lay it out by, and it adds a new rendering dependency for a presentation choice `mvp.md` explicitly says isn't required."_ `docs/product/mvp.md`'s "Entry Points and Relationships" section states _"Plain lists and tables are sufficient. An interactive graph is not required,"_ and `docs/product/non-goals.md` separately lists _"interactive dependency graphs"_ as an explicit MVP exclusion. ADR-0008 built `deriveAreaRelationships` (`src/lore/area-relationships.ts`) instead — a pure, presentation-layer rollup of file-level `depends-on` edges to Major-Area-to-Major-Area edges, rendered as a plain table (Architecture's "How areas connect" section).

A `product-scope-guardian` review, run for this specific proposal before this ADR was written, evaluated a narrower version of the diagram ADR-0008 rejected: **area-level only** (never file-level), **presentation-only** (no new analysis capability — reusing `deriveAreaRelationships`'s existing output as-is), and **non-interactive** (no pan/zoom/drag/click-to-filter). It recommended building this, with specific guardrails against scope creep (detailed in Decision, below). The product owner reviewed this and made a deliberate, informed decision to accept the resulting scoped exception to `mvp.md`/`non-goals.md`'s "plain lists and tables only" default — this ADR records that decision and its boundaries, and supersedes ADR-0008's "Static area-only diagram" rejection specifically (ADR-0008's other three rejections — architectural-boundaries narrative claims, infrastructure/data-store detection, and framework detection beyond React — are unaffected and remain in force).

## Decision

1. **New dependency: `@dagrejs/dagre`**, used for layout computation only — computing node positions and edge routing for a directed graph. No DOM binding, no React binding, no interactivity of any kind. Both `OverviewContent.tsx` and `ArchitectureContent.tsx` are plain server components (no `"use client"`), so the diagram is computed and rendered entirely server-side as static SVG; `@dagrejs/dagre` itself is never included in the client JavaScript bundle.
2. **New pure module `src/lore/area-diagram-layout.ts`** (`deriveAreaDiagramLayout`, mirroring `area-relationships.ts`'s style) computes node positions and edge paths from `StructuralArea`s and the `AreaRelationship`s `deriveAreaRelationships` already produces — no new relationship data, no new analyzer capability, no `src/lore/model.ts` changes.
3. **A node-count ceiling** (`MAX_DIAGRAM_AREAS = 30`). Above this, `deriveAreaDiagramLayout` returns `null` and callers fall back to table-only, so the diagram can never degrade into an unreadable hairball for a large repository.
4. **New presentation component `src/components/lore-shell/AreaDependencyDiagram.tsx`** renders the layout as static SVG: `<path>` edges with arrowheads, `<foreignObject>` node boxes built from the existing design-system Tailwind tokens (`bg-tile-core-bg`, `border-border`, `text-foreground`, etc.), each labeled with the area's name and (if present) its `responsibility`. No pan, zoom, drag, or click-to-filter. Node boxes are ordinary hyperlinks (`<a href={areaUrl(...)}>`) — the same interaction every other list/table in the app already has via `SourceLink`, not new interactivity.
5. **No cycle-detection callouts.** `dagre` may internally break a cycle to compute a layout when two areas mutually depend on each other; this renders as ordinary bidirectional edges, never surfaced as a "circular dependency" badge or warning. Flagging that would be a new analysis finding — a generalized health finding — which remains out of scope regardless of this decision.
6. **Embedded on both Architecture and Overview.** On Architecture (`ArchitectureContent.tsx`), the diagram sits above the existing "How areas connect" table, which stays as-is — it retains the `Certainty` column and evidence-oriented `SourceLink`s the diagram doesn't attempt to replace. On Overview (`OverviewContent.tsx`), the diagram **replaces** the raw per-file `lore.relationships` table entirely; the section is renamed "How Areas Connect" (matching Architecture's heading) and paired with a "View full architecture" link to `/lore/{owner}/{repo}/architecture`, matching `docs/designs/repository-overview.png`, which has no raw relationships table on its Overview view at all.
7. **The exception is strictly area-level.** It does not extend to file-level `Relationship` edges (`lore.relationships`) — those remain underlying data only, never rendered as a graph or diagram anywhere. Any future extension (file-level diagrams, interactivity, cycle findings surfaced as claims) needs its own ADR and `product-scope-guardian` review, per ADR-0008's own precedent for scoping follow-on work.

## Rationale

**What's different from ADR-0008's rejection.** That decision rejected a "layered box diagram with per-node framework tags... plus a narrative 'boundaries' section" for the _whole_ Architecture page, citing the lack of a diagram library, the lack of a layer/tier concept in the model, and that `mvp.md` doesn't require it. This proposal is materially narrower: it needs no layer/tier classification (dagre lays out a plain directed graph, not swim lanes), carries no narrative claims, and needs no infrastructure/framework detection. The remaining objection — "adds a new rendering dependency for a presentation choice `mvp.md` says isn't required" — is a judgment the product owner is now making deliberately and explicitly, informed by a scope review, rather than a default to avoid.

**Library choice.** `@dagrejs/dagre` (the maintained fork; the original `dagre` package is stale) is chosen over:

- **react-flow** (or similar full graph-component libraries) — rejected. Their entire value proposition is interactivity (pan/zoom/drag/minimap/controls), which stays explicitly out of scope; installing an interactive-first library invites "since it's already there" interactivity creep, and it's a heavier, faster-moving dependency than this problem justifies.
- **viz.js / Graphviz-WASM** (matching Madge's literal rendering engine) — rejected. It would cost roughly 2MB of WASM plus a DOT-string generation/escaping layer as a new source of bugs, for marginal visual difference at the node counts area-level diagrams actually have (single digits to a few dozen). Since dagre runs server-side only, the usual "client bundle size" argument for a lighter library doesn't even apply in dagre's favor here — its own size is irrelevant, because it's never sent to the browser.
- **A hand-rolled layout algorithm with no new dependency** — rejected. A correct, cycle-tolerant, non-overlapping layered layout is real algorithmic work to get right and keep right against arbitrary real-world repositories submitted by users. For a solo maintainer at 5–8 hrs/week, a small, mature, purely computational dependency (no DOM/runtime surface, easy to remove) is the better maintenance bet than debugging a bespoke layout.

**Scope discipline.** Each guardrail in the Decision above closes a specific risk raised during review: the node-count ceiling prevents an unreadable diagram forcing pan/zoom/search back into scope by necessity; the "no interactivity" rule prevents scope creep from a library that's technically capable of more than what's used; the "no cycle callouts" rule prevents a presentation change from quietly becoming a new analysis capability (health finding); and the "area-level only" rule keeps file-level relationships — the highest-volume, least-prioritized data in the model — off the table entirely, consistent with `mvp.md`'s existing guidance that relationships should be prioritized for mental-model value, not exhaustively displayed.

## Consequences

- New dependency: `@dagrejs/dagre` (`package.json`/`package-lock.json`), server-only usage — never included in the client JS bundle, since neither `OverviewContent.tsx` nor `ArchitectureContent.tsx` is a client component.
- New files: `src/lore/area-diagram-layout.ts` plus `src/lore/__tests__/area-diagram-layout.spec.ts`, and `src/components/lore-shell/AreaDependencyDiagram.tsx`.
- `ArchitectureContent.tsx` and `OverviewContent.tsx` both changed to embed the diagram. Overview's raw file-level relationships table is removed entirely, superseded by the area-level diagram plus a link to Architecture.
- `docs/product/mvp.md`'s "Entry Points and Relationships" section and `docs/product/non-goals.md`'s "interactive dependency graphs" exclusion are both amended to record this as a documented, narrow exception, so neither document silently contradicts the shipped product.
- File-level relationships (`lore.relationships`) remain undiagrammed and list/table-only — no change to that data or how it's presented anywhere.
- Any future request to diagram file-level relationships, add interactivity to this diagram, or surface cycles/orphan-areas as findings needs its own ADR and `product-scope-guardian` review, per this ADR's own Decision item 7.

## Alternatives considered

**Leave Overview's raw file-level table as-is, accept ADR-0008's diagram rejection permanently.** Rejected: the product owner explicitly found the raw per-file table clunky and uninformative, and it directly contradicts `mvp.md`'s own framing that relationships should be prioritized for mental-model value "rather than displaying every available edge" — a table of every import edge in the repository is the literal thing that guidance warns against.

**Reuse Architecture's existing `deriveAreaRelationships` table verbatim on Overview instead of a diagram** (area-level table, not a diagram). This remains a smaller, still-fully-compliant-with-non-goals option, and was seriously considered. Rejected in favor of the diagram because the product owner made a deliberate, informed choice that a visual summary better serves the "orientation confidence" promise for major-area relationships specifically, and the guardian review found the diagram an acceptable, narrowly-scoped, low-maintenance addition rather than a necessary compromise.

**Full mockup-style diagram fidelity** (swim lanes, per-node framework tags, boundary narrative — the version ADR-0008 rejected outright). Not reconsidered here: nothing in this proposal or its review changes ADR-0008's reasoning for infrastructure detection, expanded framework detection, or narrative architectural claims, all of which remain rejected.
