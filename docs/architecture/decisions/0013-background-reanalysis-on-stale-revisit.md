# ADR-0013: Pull-triggered background re-analysis on a stale revisit — a bounded exception to the "no scheduled refresh" non-goal

## Status

Accepted

## Context

GitHub issue #12 asked to "force reanalyze" a repository whenever its latest analysis is more than a day old, guarded by two checks: skip if the last analysis is under a day old, and skip if the default branch's HEAD commit hasn't moved since the analyzed commit.

The first implementation of this issue (2026-09-16, see `docs/architecture/implementation-plan.md`) stopped short of the issue's literal ask: `product-scope-guardian`, run before any code was written, found that an automatic, unattended re-analysis triggered by a page view conflicts with `docs/product/mvp.md`'s and `docs/product/non-goals.md`'s explicit "no scheduled refresh" exclusion, and flagged real operational risk in triggering a full tarball fetch/extraction synchronously off a page load (GitHub API cost tied to visitor count rather than repo count, an unlucky visitor eating full analysis latency, no worker/queue per ADR-0001/ADR-0004 to run it off the request path). The product owner accepted that finding and shipped a scoped-down version instead: a passive, dismissible banner on the Overview page pointing at the existing manual "Re-analyze" button once the latest analysis is a day old — no automatic trigger.

The product owner then reconsidered the distinction the guardian drew between "scheduled" (cron/webhook, no viewer) and "pull-triggered by a page view" (still automatic from a visitor's perspective, in the guardian's framing). Their actual intent for "no scheduled refresh" was narrower: it rules out **headless** background jobs — anything that runs with nobody visiting, on a timer or a webhook, consuming compute and GitHub API quota for repositories nobody is currently looking at. It was never meant to rule out re-analyzing a stale repository automatically **at the moment a real person visits it**, gated by the same day-old threshold. This ADR revises the implementation to match that intent, directly addressing each operational-risk point the guardian raised rather than arguing past them.

## Decision

1. **Trigger stays pull-based, gated by the same staleness check** (`isAnalysisStale`, `src/helpers/is-analysis-stale.ts`, unchanged from the 2026-09-16 work): only ever considered when someone requests a `/lore/{owner}/{repo}/**` page for a repository whose latest analysis is over a day old. No cron, no webhook, no polling — if nobody visits a stale repository, nothing runs, which is the load-bearing distinction from a headless scheduled refresh.
2. **Runs in the background, after the response is sent** (`after()` from `next/server`, called from `src/app/lore/[owner]/[repo]/layout.tsx`, which already fetches the latest run for every page under this route). The visitor who triggers it sees the current (possibly stale) data immediately — their page load is not slowed by a potential tarball fetch/extraction. This directly answers the guardian's "unlucky visitor eats full analysis latency" concern. `after()` runs in the same long-running Node process Render already hosts (ADR-0001) — this is not a worker/job-queue reintroduction; ADR-0001/ADR-0004's deferral of a separate `worker` entrypoint and job table is unchanged. If the process is recycled before an `after()` callback finishes, that attempt is simply lost, same as any in-flight request would be — no different in kind from the risk an unattended manual re-analysis click already carries.
3. **Reuses the existing per-repo claim as the concurrency guard** — the background call goes through `reanalyzeAndRefreshHistory` (`src/analysis/reanalyze-and-refresh-history.ts`), the same shared function the manual "Re-analyze" button calls, which itself calls `analyzeAndPersistRepository` → `claimReanalysisAttempt` (`REANALYSIS_COOLDOWN_SECONDS`, 60s). Simultaneous visitors to the same stale, popular repository don't each start a redundant re-analysis: only the first claims it; every other concurrent attempt (manual or automatic) throws `RateLimitedError`, which the background trigger catches and silently discards (nobody is waiting on this specific response, so there's nothing to surface it to). This directly answers the guardian's "race conditions... redundant re-analysis" concern.
4. **Guard 2 from the issue (skip if HEAD is unchanged) is still not reimplemented separately** — it's what `analyzeAndPersistRepository`'s ADR-0005 idempotency check (`getAnalysisRunByKey`) already does: if the commit hasn't moved, the existing run is returned without a new tarball fetch/extraction, and — because no new row is persisted — `analyzedAt` stays at its old value, so the repo remains "stale" and gets re-checked (cheaply: just the HEAD lookup, rate-limited to once per 60s per repo) on the next visit, rather than silently going quiet forever. This bounds the GitHub API cost of an indefinitely-unvisited-but-occasionally-checked stale repo to at most one HEAD/languages lookup per minute, only while it's actually being visited.
5. **Calling `reanalyzeAndRefreshHistory` rather than `analyzeAndPersistRepository` directly matters, not just as reuse.** `analyzeAndPersistRepository` alone persists a new analysis run but does not recompute the History page's separately-cached `history_entries` row (GitHub issue #13). A background trigger that only called it would reopen that exact bug through a new, unattended path — the visitor who unknowingly triggered a new run would have no "Re-analyze" click to also trigger a History refresh alongside it, the way the manual button's fix depends on. Caught during this ADR's own manual verification (see `docs/architecture/implementation-plan.md`'s 2026-09-17 entry) before it shipped, and fixed by extracting the manual button's existing analyze-then-conditionally-refresh-History logic into this one shared function, used by both callers.
6. **The Overview banner's copy changes to describe automatic background work instead of asking for a click** (`src/components/lore-shell/StaleAnalysisCard.tsx`): "Analyzed N days ago — checking for a newer commit in the background. Reload in a moment to see updated results." The manual "Re-analyze" button stays visible and functional (unchanged) — a visitor who doesn't want to wait can still force the same claim/attempt themselves, and gets the same honest `RateLimitedError` message if the background attempt already has it claimed.
7. **The trigger lives in the shared layout, not just Overview** — `layout.tsx` already fetches the latest run once per `/lore/{owner}/{repo}/**` request for the sidebar's visibility badge, so scheduling the background attempt there covers every page (Overview, Architecture, Dependencies, Data Flow, History), not only Overview. The banner itself stays Overview-only (unchanged design decision from the 2026-09-16 work) — the mission's "within 15 minutes of opening a Lore" framing centers on that landing page, and showing the same notice on every subpage would be UI sprawl for a background action that needs no per-page acknowledgment.
8. **Failed runs are excluded** — same as the 2026-09-16 banner, a previously-`failed` run is not automatically retried by this trigger; `FailedRunPanel`'s existing manual "Re-analyze" stays the only path to retry a failure, avoiding stacking "this is automatically retrying" messaging on top of "this failed" messaging.
9. **`revalidatePath`/`revalidateTag` are deliberately not called from the `after()` callback.** `/lore/{owner}/{repo}/**` pages read `getLatestAnalysisRunForRepo` directly from Postgres on every request (no Next.js fetch cache or `unstable_cache` wraps it — see `page.tsx`'s own doc comment, "Not a static/cached page"), so there is no route cache entry for a background revalidation to invalidate. A later visit (by anyone, including the same visitor reloading) simply queries Postgres again and sees whatever the background attempt persisted, with no extra step needed.
10. **This ADR narrows, rather than removes, the "no scheduled refresh" non-goal.** `docs/product/non-goals.md` and `docs/product/mvp.md` are both amended to state plainly that the exclusion is about headless/unattended refresh (cron, webhooks, polling with no viewer) — a pull-triggered, staleness-gated, per-repo-rate-limited background re-analysis attempt tied to an actual page view is in scope, referencing this ADR. `CLAUDE.md`'s summary line is updated to match.

## Rationale

**Why "headless" is the right line, not "automatic."** The guardian's original framing — any trigger a visitor didn't explicitly click is indistinguishable from scheduled refresh — is defensible in the abstract, but it would also forbid things like a cache warming on first request, which nobody would call "scheduled." What actually motivates a solo maintainer's "no scheduled refresh" instinct is unattended cost: compute and GitHub API quota spent on repositories nobody is currently looking at, on a cadence outside anyone's control. A trigger that only ever fires because a real person's request just arrived, gated by a coarse staleness threshold and rate-limited per repo, doesn't have that property — the cost is bounded by and proportional to actual traffic, the same way the existing manual "Re-analyze" button's cost already is.

**Why background instead of synchronous.** A synchronous auto-trigger (run inline before rendering) was considered and rejected for the same reason the guardian originally flagged: it makes page-load latency for a stale repo unpredictable and, for a large repository, potentially very slow — exactly the kind of UX regression a solo-maintained MVP shouldn't accept for a "nice to have automatically fresher" feature when a background attempt gets the same eventual result without that cost.

**Why reusing `claimReanalysisAttempt` instead of a new mechanism.** A separate cooldown/lock for the automatic path was considered (see Alternatives) but rejected — the manual button and the automatic trigger both want exactly the same property (at most one in-flight `analyzeAndPersistRepository` attempt per repo at a time), so sharing the claim is simpler and means there's only one rate limit to reason about, not two that could interact confusingly (e.g. a manual click right after an automatic one silently doing nothing because a _different_ cooldown hasn't expired yet, with no way for the UI to explain why).

## Alternatives considered

**Synchronous auto-trigger on page load** (the issue's literal shape). Rejected — see Rationale; unpredictable, potentially large page-load latency for the visitor who happens to hit a stale repo.

**A separate cooldown for the automatic trigger, distinct from `REANALYSIS_COOLDOWN_SECONDS`.** Rejected — see Rationale; two independent locks on the same underlying resource (one repo's analysis) is more state to reason about for no behavioral benefit, since both paths want the same "one attempt at a time" property.

**A real background worker/job queue** (ADR-0001/ADR-0004's deferred target shape) to run the re-analysis, instead of `after()` inline in the same process. Rejected for now — `after()` on Render's long-running process gets the same "doesn't block the response" property without standing up a queue table, a worker entrypoint, or polling, none of which this feature's scale justifies yet. Revisit if/when ADR-0004's deferral is revisited for other reasons.

**Auto-retrying a `failed` run when stale.** Considered, since a stale failure could be a transient GitHub hiccup rather than a persistent problem. Deferred — see Decision point 7; not needed for this ADR's scope, and stacking automatic-retry messaging onto `FailedRunPanel`'s existing manual-retry framing needs its own design pass.

## Consequences

- `src/analysis/reanalyze-and-refresh-history.ts` (new) — `reanalyzeAndRefreshHistory(owner, repo) → { run, changed, historyRefreshed }`: extracted from the manual "Re-analyze" Server Action's previously-inline logic so both it and the new background trigger keep History in sync the same way (see Decision point 5).
- `src/analysis/background-reanalysis.ts` (new) — `scheduleBackgroundReanalysisIfStale(owner, repo, analyzedAt)`, calling `after()` around `reanalyzeAndRefreshHistory`, silently discarding `RateLimitedError` and logging any other error.
- `src/app/lore/[owner]/[repo]/layout.tsx` — calls `scheduleBackgroundReanalysisIfStale` for a non-`failed` run with a result, using the same `run` it already fetches.
- `src/app/actions.ts`'s `reanalyzeRepository` — now calls `reanalyzeAndRefreshHistory` instead of inlining the same logic, keeping only the Server-Action-specific parts (`revalidatePath` for `/lore/{owner}/{repo}` always, `/lore/{owner}/{repo}/history` only when `historyRefreshed`).
- `src/components/lore-shell/StaleAnalysisCard.tsx` — copy changed to describe automatic background checking rather than asking for a click; still dismissible; the manual "Re-analyze" button is untouched.
- `docs/product/non-goals.md` and `docs/product/mvp.md`'s "scheduled refresh" exclusions are both narrowed to specifically name headless/unattended triggers (cron, webhooks, polling), with a reference to this ADR for the pull-triggered, staleness-gated exception. `CLAUDE.md`'s summary line is updated to match.
- No new infrastructure, dependencies, database tables, or worker process — this reuses `analyzeAndPersistRepository`, `claimReanalysisAttempt`, `computeHistory`/`saveHistoryEntries`, and `next/server`'s `after()`, all already present.
- A repository that is stale but never visited is never re-analyzed — this remains true and is the intended behavior, not a gap.
