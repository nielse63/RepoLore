# ADR-0008: The first real Architecture page renders only existing Lore-model data, as lists/tables

## Status

Accepted

## Context

`/lore/{owner}/{repo}/architecture` (`src/app/lore/[owner]/[repo]/architecture/page.tsx`) currently renders entirely hardcoded example content from `src/lib/fixtures/payments-service.ts` (an imaginary `acme/payments-service` repo), matching `docs/designs/architecture.png`'s mockup, with a `PreviewBanner` disclosing it isn't real. It's one of several Lore sub-pages scaffolded this way (`systems`, `dependencies`, `data-flow`, `history`, `search` remain out of scope for this decision); only the root `/lore/{owner}/{repo}` overview page currently renders real, persisted analysis data via `getLatestAnalysisRunForRepo`.

Replacing this page's example content with real data surfaced a hard mismatch between the mockup and what the analysis pipeline can actually produce today:

- **The mockup** shows a layered box diagram — four swim lanes ("Entry points", "Core services", "Background processing", "Data stores"), each with named component boxes carrying a per-node framework/tech label ("API Gateway · FastAPI", "Worker · Celery", "PostgreSQL · Primary DB"), connected by directional arrows (solid for sync, dashed for async/queue-based) — plus an "Architectural boundaries" section: narrative claims about system-wide behavioral invariants ("The API layer owns request validation. All incoming requests are validated at the API layer before reaching core services." — "Supported by 14 references").
- **Nothing in the codebase supports this today.** No infrastructure/data-store detection exists anywhere (no `pg`/`redis`/`sqlalchemy`/`celery`/docker-compose heuristics). No framework detection exists beyond JS/TS's React heuristic — Python's `Project.frameworks` is always `[]`. No layer/tier classification concept exists anywhere in `src/lore/model.ts` (`StructuralArea.responsibility` is the closest thing, populated today only with `"Tests"`, `"Test fixtures/support data"`, `"Build/tooling configuration"`, or a React label). No diagram/graph-rendering library is installed (no d3, mermaid, react-flow, dagre, cytoscape).
- **`Relationship` is strictly file-to-file.** Only the `depends-on` `RelationshipKind` is ever constructed, from syntactic import edges (JS/TS via ts-morph, Python via tree-sitter). `depended-on-by`, `exports-to`, and `cross-language` are declared in the model but never built anywhere. `StructuralArea.directDependencyIds`/`directDependentIds` are a same-project, one-directory-level-deep rollup of those file edges (`src/analysis/shared/derive-views.ts`) — there is no cross-project or cross-language relationship data.
- **A claim like "all incoming requests are validated at the API layer" requires call-graph/flow analysis** the syntactic, non-type-checked ts-morph/tree-sitter analyzers cannot produce. Attempting it risks exactly the overclaiming `docs/product/mvp.md`'s Major-Area Detection Model warns against ("Do not invent business-domain names or expand narrow evidence into broad architectural claims") and that `docs/product/non-goals.md` explicitly excludes from the MVP ("complete execution-flow or data-flow tracing," "complete framework-specific behavioral interpretation," "architectural diffs or pull-request impact analysis"). `docs/product/mvp.md`'s "Entry Points and Relationships" section is also explicit that "Plain lists and tables are sufficient. An interactive graph is not required," and `non-goals.md` separately excludes "interactive dependency graphs."

A `product-scope-guardian` review, run before this ADR was written, evaluated four specific pieces of mockup fidelity — the architectural-boundaries narrative section, infrastructure/data-store detection, framework detection beyond React, and the box-and-arrow diagram — against mission alignment, MVP necessity, maintenance cost, operational risk, and simpler alternatives. It recommended rejecting all four for a first real version, in favor of rendering only what the `Lore` model already produces. The product owner confirmed this scope.

## Decision

1. **Render only existing `Lore`-model data.** The first real Architecture page uses `Project` (kind, languages, frameworks, root path), `StructuralArea` (name, location, rationale/responsibility, entry points, evidence, gaps), `EntryPoint`, and an area-to-area relationship view **derived from the already-computed** `StructuralArea.directDependencyIds`/`directDependentIds` — a presentation-layer transformation resolving area IDs to area names/locations. No new analyzer capability and no `src/lore/model.ts` changes are required.
2. **No new analyzer work.** No infrastructure/data-store detection, no framework detection beyond what JS/TS (React) and Python already produce, no layer/tier classification are added as part of this decision.
3. **No "Architectural boundaries" narrative-claims section.** Where the model already declares a `RelationshipKind` that's never constructed (`exports-to`, `cross-language`), or an unresolved/unsupported construct, that surfaces through the existing `Gap` mechanism (`unknown`/`unsupported` certainty), not as a fabricated system-wide claim.
4. **No diagram/graph rendering.** The page is built from the same list/card/table primitives the real Overview page already established (`OverviewContent.tsx`; `Card`, `Table`/`Thead`/`Th`/`Tr`/`Td`, `SourceLink`, `CertaintyBadge`, `IconTile` from `src/components/ui/`), differentiated from Overview by grouping content per `Project` (relevant for mixed-language repositories, per ADR-0007) and by an explicit area-to-area "how areas connect" table distinct from Overview's raw file-to-file relationships table.
5. **`PreviewBanner`/`PreviewActions` and the fabricated right-rail stats are dropped once real**, matching the precedent the real Overview page already set — replaced with genuine data: an evidence-reference count actually derived from the rendered areas/relationships/entry points, and `snapshot.analyzedAt` via the existing `relativeTime` helper (as `AnalysisRail` already does).
6. **`docs/designs/architecture.png` remains the visual-language reference** (right-rail info card, section headers, card/list patterns) but not a literal data-content target for this version. This ADR narrows what CLAUDE.md's "UI work must be based on the mockups" instruction means for this specific view, consistent with `docs/product/non-goals.md`'s own stated precedence: "The detailed MVP specification is the source of truth when another document appears to conflict with this one."

## Rationale

Each rejected piece independently fails the MVP-necessity or operational-risk bar for a solo-maintainer, MVP-stage product (`product-scope-guardian` findings):

- **Architectural boundaries (narrative claims):** Absent from `mvp.md`'s Minimum Value Contract entirely; the nearest analog ("Things to Investigate") is scoped to narrow, high-confidence prompts, not system-wide behavioral guarantees. The maintenance cost has no natural stopping point (each claim needs continuous heuristic tuning and wording review to avoid overclaiming), and the operational risk is the highest of anything considered here: a wrong claim here is precisely the "high confidence paired with incorrect answers" failure mode `mvp.md`'s Success Test calls a product failure, with direct trust cost to a paying customer. The simpler alternative — a factual "Boundary crossings" list built from `directDependencyIds`/`directDependentIds` and `Relationship`, phrased as Detected/Inferred facts ("packages/api directly depends on packages/worker (3 imports)"), never invariant language ("owns," "all," "before reaching") — delivers a comparable orientation signal without the overclaiming risk.
- **Infrastructure/data-store detection:** Wholly new analyzer surface with no natural stopping point (each dependency — Postgres, Redis, Kafka, ... — needs its own detection rule, evidence, and tests) and medium-high operational risk (labeling Redis as "Cache & Queue" is an inferred _usage_ claim current evidence can't fully justify — the same class of behavioral interpretation `non-goals.md` excludes). Absent from `mvp.md`'s Minimum Value Contract.
- **Framework detection beyond React:** Aligned with the model in principle (`Project.frameworks` already exists as a field), but FastAPI/Flask/Django/Express/Celery detection is Python/JS-_analyzer_ work, not Architecture-_page_ work — bundling it into this decision expands its blast radius for no v1 necessity. The page can render whatever `Project.frameworks` already contains today and disclose the rest as an existing `Gap`.
- **Diagram rendering:** `mvp.md` states a default bias toward lists/tables and that an interactive graph is "not required"; a static diagram isn't literally excluded, but it introduces a new rendering dependency (no diagram library exists in the project) for a layout problem the model can't currently classify well (no layer/tier concept), and without the infra/framework detection rejected above, most real repositories won't naturally sort into "Entry points / Core services / Background processing / Data stores" anyway — the diagram would degenerate into an unhelpful default for most real repositories submitted.

## Consequences

- No `src/lore/model.ts` changes.
- New/changed application code is confined to a new architecture-page content component (e.g. `src/components/lore-shell/ArchitectureContent.tsx`), a small pure helper resolving `StructuralArea` dependency/dependent IDs into an area-name relationship table, and rewiring `src/app/lore/[owner]/[repo]/architecture/page.tsx` to the real data-fetch pattern the Overview page already established (`getLatestAnalysisRunForRepo` → branch on failed/no-result → render).
- `src/lib/fixtures/payments-service.ts`'s `ARCHITECTURE_LAYERS`/`ARCHITECTURAL_BOUNDARIES` exports become unused by the real Architecture page (left in place — still used by other still-fixture-backed routes, e.g. `systems`).
- Mixed-language repositories (ADR-0007) render one Architecture section per `Project`, matching the aggregation pattern `AnalysisRail`/`RepoIdentity` already use.
- The rejected pieces (data-store detection, expanded framework detection, boundary narratives, diagram rendering) remain available as later, independently-scoped work — each would need its own ADR and `product-scope-guardian` review before starting, per this ADR's own reasoning.

## Alternatives considered

**Static area-only diagram** (keep a non-interactive box diagram of Major Areas and their direct Relationships, dropping only the infra/framework/boundaries pieces) was considered as a middle ground. Rejected: no diagram library exists yet, `StructuralArea` has no layer/tier concept to lay it out by, and it adds a new rendering dependency for a presentation choice `mvp.md` explicitly says isn't required — the same list/table primitives already used by the real Overview page can convey the same relationships without it.

**Full mockup fidelity** (build infrastructure detection, expanded framework detection, layer/tier classification, and boundary-narrative generation now, to match `architecture.png` exactly) was rejected per the `product-scope-guardian` review: each piece independently fails the MVP-necessity and operational-risk bar for this product stage, and the boundary-narrative section specifically risks the Success Test's named failure mode (high confidence paired with incorrect answers). This work remains available later, as separately-scoped, separately-reviewed capability.
