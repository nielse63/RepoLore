# ADR-0012: Function-level call graph — a bounded, interactive exception to ADR-0009's file-level boundary and to two `non-goals.md` exclusions

## Status

Accepted

## Context

`/lore/{owner}/{repo}/data-flow` rendered 100% hardcoded example content (`DATA_FLOW_STEPS` in `src/lib/fixtures/payments-service.ts`), matching `docs/designs/data-flow.png`'s mockup: a system/service-level narrative journey (Client → API Gateway → Auth Service → Payment Service → PostgreSQL → Worker → Notification Service) with inputs/outputs/state-change per step. The page's own on-screen banner already disclosed "Data-flow tracing isn't implemented yet — see docs/product/mvp.md's MVP exclusions." That mockup describes a microservices runbook Repo Lore has no analyzer capability to produce (no infrastructure/service-boundary detection exists or is planned — ADR-0008 rejected that outright) and is unrelated to what this ADR builds.

The product owner asked instead for a **function-level call graph**: for any function, see what calls it and what it calls, in which files, with argument/return types where statically knowable, searchable by function name, with click-to-drill-down into a specific function's full chain regardless of its position in it. Two documents already speak directly against pieces of this:

- `docs/product/non-goals.md` excludes "complete execution-flow or data-flow tracing."
- `docs/product/non-goals.md` also excludes "interactive dependency graphs (pan, zoom, drag, click-to-filter, or similar) — at the file level, or otherwise," with ADR-0009's static, non-interactive, area-level diagram carved out as the only exception — and ADR-0009 itself states plainly: "This exception does not extend to file-level relationships... Any future extension (file-level diagrams, interactivity...) needs its own ADR and `product-scope-guardian` review."

A `product-scope-guardian` review was run against a draft of this proposal before this ADR was written. It found the underlying distinction sound (a _call graph_ — static reachability, "who mechanically calls whom" — is materially narrower than _value-level data-flow tracing_, which would claim a specific argument or return value propagates from one call to another), but required that this ADR explicitly extend ADR-0009's boundary rather than argue past it, amend both `non-goals.md` bullets above rather than silently ignore them, rename on-page language away from "Data Flow" so the UI doesn't imply a stronger claim than the analysis makes, and adopt a resolution discipline that never fabricates a call edge. It also flagged a real usability risk: syntactic-only call resolution mechanically cannot follow method calls (`obj.foo()`, `this.foo()`), callbacks/higher-order calls, or dynamic dispatch — the dominant call shapes in real JS/TS and Python — so many real repositories will show a sparser graph than a human would expect from reading the code. The product owner reviewed this risk and chose to proceed with the interactive graph directly (not the guardian's suggested "plain table first" sequencing), accepting that risk as an honest, disclosed limitation rather than a correctness defect.

## Decision

1. **Two new model entities** (`src/lore/model.ts`), distinct from the existing file-level `Relationship`/`RelationshipKind` (which stays import/export-only and is unmodified):
   - `CallableSignature` — a named function, method, or named arrow/function-expression: `id`, `name`, `kind` (`"function" | "method" | "arrow" | "function-expression"`), `location`, `parameters` (`{ name, typeAnnotation?, certainty }[]`, certainty restricted to `"detected" | "unknown"`), `returnType?`, `returnCertainty` (same restricted certainty), `evidence`.
   - `CallEdge` — a statically-resolved call from one `CallableSignature` to another: `id`, `callerId`, `calleeId`, `callSiteLocation`, `certainty` (restricted to `"detected"` — an edge is only ever created when mechanically resolved; there is no "inferred" call edge), `evidence`. `Lore` gains `callableSignatures: CallableSignature[]` and `callEdges: CallEdge[]`.
   - Anonymous function expressions and arrow functions (not assigned to a variable or property) are **not** tracked as `CallableSignature`s — there is no name to search for or display, mirroring `react-components.ts`'s existing `componentName` fallback logic but choosing to omit rather than label `<anonymous>`.
2. **JS/TS extraction** (`src/analysis/js-ts/call-graph.ts`): enumerates named function declarations (including nested ones), named class methods, and named arrow/function-expressions (assigned to a variable or property) across all discovered source files. Parameter and return types are read **only from explicit source annotations** (`ParameterDeclaration.getTypeNode()` / the function's `getReturnTypeNode()`, verbatim text) — never inferred, never type-checked (ADR-0003's syntactic-only scope is unchanged; no `tsconfig`-driven type-checked `Program` is introduced). An unannotated parameter or return is `"unknown"`, honestly, never guessed.
3. **Call resolution discipline — deliberately narrower than "every unresolved call is a gap":**
   - Only **plain-identifier calls** (`foo()`) are attempted at all. Property-access calls (`obj.foo()`, `this.foo()`), computed calls (`obj[x]()`), and any call whose callee expression isn't a bare identifier are out of scope for this version and are never recorded as an edge, a gap, or a partial result.
   - A plain-identifier call resolves to a `detected` `CallEdge` only when the identifier unambiguously matches either (a) a named callable declared in the same file, or (b) a named callable reached through a **named** (not default) import resolved the same way `imports.ts`/`module-resolution.ts` already resolve relative specifiers for file-level edges.
   - A call whose nearest enclosing function is itself anonymous/untracked, or that sits at module scope, is not attributed to any caller and is skipped.
   - Everything else that doesn't resolve (calls to external packages, globals, default-imported callables, ambiguous same-named matches, or values held in a variable/callback) is **silently out of scope — not recorded as a per-call-site `Gap`.** This mirrors the existing, already-established precedent in `module-resolution.ts` for asset imports and bare external specifiers: recording a `Gap` for every one of these would flood the model exactly the way the pre-fix `react-weather-app` run produced 68 spurious "could not resolve" gaps for ordinary asset imports (implementation-plan session 6) — except here the volume would be far larger, since method calls and callbacks are the _majority_ call shape in real code, not an edge case. The limitation is disclosed once — in this ADR and in the page's own UI copy — not modeled as per-instance data.
4. **A node cap, `MAX_CALL_GRAPH_NODES = 40`**, on any single rendered subgraph, mirroring `MAX_DIAGRAM_AREAS`'s role in ADR-0009. The UI never renders the whole repository's call graph at once — only one function's local subgraph (its callers and callees, transitively in both directions) up to the cap. If the reachable set from a chosen focus function exceeds the cap, the UI falls back to direct callers/callees only (one hop) with an explicit "chain truncated — showing direct relationships only" disclosure, the same fallback shape ADR-0009 established for `deriveAreaDiagramLayout`.
5. **Client-side interactivity, reusing `@dagrejs/dagre` rather than adding a new graph library.** This is the one deliberate, explicit extension of ADR-0009's "no interactivity" rule — required because search-to-focus and click-to-drilldown are the feature's core value, not an add-on. `dagre` (already a dependency, pure layout computation, no DOM/React binding) computes node positions client-side for the bounded local subgraph described in point 4; a full interactive graph library (react-flow, cytoscape, vis-network) was evaluated and rejected for the same reason ADR-0009 rejected them at the area level — their value proposition is pan/zoom/minimap/large-graph performance, which this feature never needs, since the rendered surface is always small and local by construction. Layout is recomputed fresh on every focus change (a new bounded subgraph), never incrementally patched, keeping the client logic simple.
6. **The page is renamed, in its on-screen copy only, from "Data Flow" to "Data Flow."** The URL (`/lore/{owner}/{repo}/data-flow`) is left unchanged for reversibility (no incoming links break), but the heading, description, and any UI copy must not imply value-level data-flow tracing, consistent with the guardian's requirement that the feature not overclaim what it does.
7. **JS/TS only in this ADR.** Python call-graph extraction (`tree-sitter-python`, same discipline) is explicitly deferred to its own follow-on ADR and implementation-plan session, matching this project's established JS/TS-then-Python sequencing (the original extractor, `external-dependencies.ts`/ADR-0011). `Lore.callableSignatures`/`callEdges` are empty for a Python-only analyzed project until that follow-on ships.
8. **Backward compatibility and versioning** (ADR-0005/ADR-0011 precedent): `JS_TS_ANALYZER_VERSION` bumps `js-ts-v6` → `js-ts-v7`. `src/db/analysis-runs.ts`'s `mapRow`/`normalizeResult` normalizes `result.callableSignatures`/`result.callEdges` to `[]` when reading a pre-existing row whose stored JSON predates this field.
9. **This ADR extends ADR-0009's boundary and amends two `non-goals.md` bullets.** ADR-0009's area-level diagram, its non-interactivity, and its "does not extend to file-level relationships" statement are otherwise unchanged — this ADR does not retroactively make the area diagram interactive or extend it to file-level edges. It only grants a new, separately-scoped exception at the function-call-graph level. `non-goals.md`'s "complete execution-flow or data-flow tracing" and "interactive dependency graphs... at the file level, or otherwise" bullets are both amended to record this scoped exception, the same way ADR-0009 amended `non-goals.md` for the area-level diagram.

## Rationale

**Call graph vs. data-flow tracing.** Non-goals.md's exclusion targets exactly what it says: tracing that a specific value flows from one point to another. A call graph makes a narrower, cheaper-to-justify claim: that one function's body contains a call to another. The distinction is real, but naming the page "Data Flow" would have undercut it in the UI regardless of what the ADR says — hence the rename requirement.

**Why not gap-flood every unresolved call.** The alternative — treating every method call, callback, or dynamic dispatch as an explicit per-call-site `Gap` — was seriously considered, since it's the literal reading of "everything unresolved is an honest gap" applied elsewhere in this codebase (e.g. unresolved relative imports). It's rejected here for the same reason `looksLikeAssetImport` exists: some categories of "can't resolve this" are out of scope by design, not a limitation worth surfacing per instance, and the volume here would be far larger than the asset-import case that originally motivated that precedent. Disclosing the limitation once (in the ADR and the UI) is more honest in practice than burying it under thousands of identical gap entries a user would immediately learn to ignore.

**Why dagre instead of a dedicated graph library.** Identical reasoning to ADR-0009: the feature's rendered surface is always one function's bounded local neighborhood, never the whole repository's call graph, so the scaling/interactivity problem a dedicated library solves (arbitrary-size graphs, pan, zoom, minimaps) doesn't exist here. Taking on react-flow or similar for a feature that only ever renders ≤40 nodes at a time would be new dependency weight bought for capability this feature will never use, and would invite exactly the scope creep (pan, zoom, arbitrary layout) ADR-0009 already fenced off once.

**Why JS/TS only, right now.** Splitting language extraction work has been this project's default (the original extractor, `external-dependencies.ts`) for solo-maintainer pacing reasons that haven't changed. The product owner's choice to build the interactive UI immediately (rather than a table-first intermediate step) is orthogonal to that — it changes how much UI ships alongside the first language's extraction, not whether a second language's extraction work is bundled in.

## Alternatives considered

**Ship a plain list/table first, defer the interactive graph** (the guardian's actual recommendation). Rejected by the product owner for this iteration — a deliberate, informed call to accept the sparse-real-repo-graph risk now rather than sequence around it. Available again if the shipped graph proves too sparse or confusing in practice against real repositories; nothing in this ADR forecloses adding a table view alongside it later.

**Per-call-site gaps for every unresolved call.** Rejected — see Rationale; the volume would overwhelm the model's existing gap precedent rather than inform it.

**A full type-checked `ts-morph` `Program` to infer types beyond explicit annotations.** Rejected for this ADR — the product owner explicitly chose annotation-only type detection to avoid reopening ADR-0003's syntactic-only decision. Remains available as its own future ADR if annotation coverage on real repositories proves too sparse to be useful.

**A dedicated interactive graph library (react-flow, cytoscape, vis-network).** Rejected — see Rationale; over-provisioned for a feature whose rendered surface is always small and local.

## Consequences

- New application code: `src/lore/model.ts` additions (`CallableSignature`, `CallEdge`, `Lore` fields); `src/analysis/js-ts/call-graph.ts`; `src/lore/call-graph-layout.ts` (dagre-based bounded subgraph layout, mirroring `area-diagram-layout.ts`); `src/components/lore-shell/CallGraphContent.tsx` (client component: search, focus selection, SVG rendering, drilldown); the rewritten `data-flow/page.tsx`.
- `src/lib/fixtures/payments-service.ts`'s `DATA_FLOW_STEPS` export becomes unused by the real page (left in place, matching ADR-0008/ADR-0010/ADR-0011 precedent for superseded fixture content).
- `JS_TS_ANALYZER_VERSION` bump (`js-ts-v6` → `js-ts-v7`) and a `mapRow`/`normalizeResult` backward-compatibility default in `src/db/analysis-runs.ts`, per ADR-0011's established pattern. Every repository analyzed before this change needs a manual re-analysis before its Data Flow page shows real data; until then it shows an honestly empty result rather than crashing.
- `docs/product/non-goals.md`'s "complete execution-flow or data-flow tracing" and "interactive dependency graphs... at the file level, or otherwise" bullets are both amended to record this exception, referencing this ADR.
- ADR-0009 itself is not edited — its area-level diagram remains non-interactive and file-level-relationship-free; this ADR documents a separate, additional exception rather than modifying that one.
- Python call-graph extraction is deferred to its own follow-on ADR and implementation-plan session; `Lore.callableSignatures`/`callEdges` are empty for Python-only projects until then.
- Method calls, callbacks/higher-order calls, dynamic dispatch, and default-imported callables remain permanently unresolved by this version of the feature — a disclosed, structural limitation, not a bug, and not modeled as per-instance gaps. Real repositories dominated by these call shapes (e.g. heavily class-/OOP-based codebases) will show sparser call graphs than a human reading the same code would expect; this is the risk the product owner explicitly accepted rather than a defect to fix later.
