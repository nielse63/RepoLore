# ADR-0007: GitHub languages API drives analyzer dispatch, with a byte-share threshold for multi-analyzer runs

## Status

Accepted

## Context

Every real `/lore/{owner}/{repo}` submission has, since session 7, unconditionally run the JS/TS extractor (`extractJsTsProject`) against whatever the fetched tarball contains — there has never been a step that decides _which_ analyzer(s) a given repository should run. `extractPythonProject` (ADR-0006) exists and is fully validated, but nothing in the real submission path ever calls it.

This was flagged as a known gap at the end of session 13 (`docs/architecture/implementation-plan.md`) but not designed or implemented then. It surfaced as a user-visible bug: submitting `scottrogowski/code2flow` (GitHub: 49.5% Python, 27.2% JavaScript) reports `languages: ["javascript"]`, because the unconditional JS/TS run finds the repo's `.js` files and never looks for `.py` files at all. Submitting `spulec/freezegun` (GitHub: 99.8% Python, no `.js`/`.ts` files) reports `languages: []` ("none detected"), because the unconditional JS/TS run finds nothing and Python is never invoked. In both cases the "language" shown was never actually a language-detection result — it was an incidental side effect of `detectLanguages` (`src/analysis/js-ts/extract-project.ts`) tagging whatever `.ts/.tsx/.js/.jsx` files the JS/TS file-discovery glob happened to match.

Three questions had to be settled to close this gap, consistent with `docs/product/mvp.md`'s JS/TS/Python scope and the "language-neutral Lore model" the shared domain model (`src/lore/model.ts`) already supports (`Lore.projects: Project[]` is already an array):

1. What signal decides which language(s) a repository "is," given GitHub's own UI (which this bug report was compared against) computes this from byte-weighted per-file classification, not from any convention our extractors can cheaply re-derive?
2. code2flow is genuinely polyglot (a Python core with a bundled JS visualizer). Should dispatch run every supported analyzer that clears some bar, or force a single "primary" choice?
3. What should happen to a repository whose language(s) aren't JS/TS or Python at all (e.g., a Go or Ruby repo submitted by mistake)?

## Decision

1. **Signal**: call GitHub's `GET /repos/{owner}/{repo}/languages` (byte-weighted per-language totals — the same data GitHub's own UI percentage bars are computed from) as the sole authority for dispatch. `src/github/client.ts` gains `fetchRepositoryLanguages`, called once per analysis attempt alongside `resolveRepositoryHead`. We deliberately do **not** re-derive language shares by counting files in the extracted tarball (that's just re-implementing GitHub's own linguist classification worse, and is exactly the mechanism that produced this bug) and do **not** treat the tarball's file tree as a second opinion that could override GitHub's stats — GitHub's number is authoritative, full stop, so what Repo Lore reports never disagrees with what a user already sees on the GitHub repository page.
2. **Multi-analyzer dispatch**: every supported analyzer group (`js-ts` — JavaScript + TypeScript combined; `python`) whose GitHub-reported byte share is **≥ 10% of the repository's total classified bytes** is run, and every project it produces is included in the resulting `Lore.projects`. A repository can produce more than one `Project`. 10% is chosen as comfortably above incidental scaffolting (a lone build script, a vendored snippet) while comfortably below a genuine secondary language doing real work (code2flow's JS share is 27.2%). This is a disclosed, tunable constant (`MIN_LANGUAGE_SHARE_FOR_ANALYSIS` in `src/analysis/dispatch/detect-languages.ts`), the same precedent as `DEFAULT_EXTRACTION_LIMITS` (ADR-0002) and `REANALYSIS_COOLDOWN_SECONDS` — not a load-bearing design commitment.
3. **Unsupported languages get an explicit, honest state, not a silent fallback.** If no supported analyzer group clears the threshold (a pure-Go or pure-Ruby repo; an empty repo GitHub reports no languages for), the run is persisted as `status: 'failed'` with an `errorMessage` naming GitHub's actual top language(s) and stating plainly that Repo Lore only analyzes JavaScript, TypeScript, and Python — reusing the existing "failed run" rendering path (`src/app/lore/[owner]/[repo]/page.tsx`) that already exists for acquisition/extraction failures, rather than inventing a fourth status value or letting an empty/misleading result stand in for "unsupported."

Projects are ordered in `Lore.projects` by descending GitHub byte share, so `projects[0]` — still read by several call sites as a "primary project" shorthand — is always the repository's actual majority language, not whichever analyzer happened to run first.

## Rationale

Byte-weighted GitHub stats were chosen over file-tree extension counting specifically because the bug report that motivated this ADR _is_ a file-tree-counting bug: `detectLanguages` counting `.js` files told us nothing about whether those files represented 2% or 50% of the repository, and told us nothing about Python's presence at all (no Python-specific counting existed on the real submission path to begin with). GitHub's `languages` endpoint gives us, for one HTTP call already covered by the existing `GITHUB_TOKEN` (ADR-0002), the exact byte-weighted classification a user is already looking at when they compare our output to GitHub's — eliminating the class of disagreement this bug report describes by construction, not by tuning heuristics to match it after the fact.

Running every analyzer above the threshold (rather than picking one "primary" language) was chosen because `docs/product/mvp.md` explicitly frames the model as language-neutral and multi-project-capable, and a single-primary-only rule would under-serve exactly the repository shape the JS/TS + Python ecosystem produces constantly: a Python service with a JS/TS frontend or tooling layer, or vice versa. Session 14 (`docs/architecture/implementation-plan.md`) already existed to "confirm the repository-level model presents JS/TS and Python projects together" — this decision is what makes that session's premise real on the actual submission path rather than only in hand-built local fixtures.

An explicit unsupported-language state was chosen over silently continuing to run JS/TS (today's behavior) because a silent, wrong answer is worse than a stated limitation — consistent with the Detected/Inferred/Unknown/Unsupported certainty discipline `docs/product/mission.md` and the shared Lore model already apply everywhere else. It reuses the `'failed'` run status and its existing UI rather than adding a new status, since "no analyzer could produce a result" is accurately, not euphemistically, a failed run.

## Consequences

- `analyzeAndPersistRepository` (`src/analysis/analyze-and-persist.ts`) now fetches languages, calls the new dispatch module, and can invoke zero, one, or both extractors for a single submission. `acquireRepositorySource` still runs exactly once regardless of how many analyzers are selected — dispatch only decides which extractor(s) to run against the one already-fetched tarball.
- `AnalysisRunRow`/`Lore` are keyed by a single `analyzer_version` string (ADR-0005), but a repository's analyzer _set_ now varies per repository. The version key becomes a deterministic composition of the selected analyzers' own versions (e.g. `dispatch-v1:js-ts-v3+python-v2`, analyzers sorted alphabetically) via a new `src/analysis/dispatch/version.ts`, plus a dispatch-logic version component (`DISPATCH_VERSION`) bumped whenever the detection/threshold logic itself changes — so a change to the 10% threshold, the language-name mapping, or the extractor versions it composes all correctly invalidate prior runs under ADR-0005's existing idempotency contract, with no schema change.
- `buildLore` (`src/lore/build-lore.ts`) changes from accepting one extraction+views pair to an array of them, merging `projects`, `structuralAreas`, `entryPoints`, `relationships`, `publicContracts`, `testRelationships`, and `gaps` by concatenation (each language's evidence stands entirely on its own — no cross-language relationship is invented, matching session 14's explicit constraint), and rebalances `startHere` by interleaving each language's already-ordered recommendations to stay within the model's existing 3–7 item bound (`START_HERE_MIN_ITEMS`/`START_HERE_MAX_ITEMS`) rather than simply concatenating and overflowing it.
- The language-neutral `deriveViews` core (`src/analysis/shared/derive-views.ts`) namespaces structural-area IDs by `projectId` (previously just `area:${name}`, now `area:${projectId}:${name}`) — needed because two extractions merged into one Lore can otherwise independently produce a same-named area (e.g. both find a top-level `src/`) and collide.
- UI surfaces that read `lore.projects[0]` as shorthand for "the project" (`RepoIdentity`'s language badge, `AnalysisRail`, `LoreView`) are updated to aggregate across every entry in `lore.projects`, so a two-project result actually displays both languages instead of silently hiding the second one behind array-index-zero.
- This is scoped to detection/dispatch only. It does not add cross-language relationship inference, a unified multi-language Start Here beyond the interleave-and-cap rule above, or any UI redesign beyond making existing "first project" shorthands project-array-aware — a fuller mixed-language presentation remains future work.

## Alternatives considered

**File-tree extension counting** (count `.py` vs `.js/.ts/.jsx/.tsx` files found in the downloaded tarball ourselves) was rejected as the primary signal: it's strictly worse than what GitHub already computes (no byte-weighting, no comment/vendored-file exclusion, no handling of the dozens of other extensions GitHub's linguist recognizes), it's the literal mechanism that produced this bug, and duplicating it doesn't remove any real dependency — the GitHub API call is already required and already authenticated.

**Hybrid (GitHub API to choose, file tree to confirm)** — running the file-tree check as a defense against stale or unusual `languages` data — was considered and rejected for v1 as unneeded defensive complexity: GitHub's `languages` stats are computed from the same commit tree being analyzed, there's no observed failure mode this guards against, and it would reintroduce a second source of truth that could disagree with GitHub's own numbers, undermining the whole point of using them. If a concrete case of the two signals diverging in a way that matters is ever observed, this can be revisited as an additive check rather than redesigned from scratch.

**Single-primary-language dispatch** (run only the analyzer for the single largest supported language) was rejected because it would still misreport code2flow-shaped repositories — showing only Python and hiding a JS/TS share large enough to matter — and would need revisiting the moment session 14's mixed-language work landed anyway, so there was no real simplicity gained by deferring it.
